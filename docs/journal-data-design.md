# 言 · 手账数据结构定案(城市容器 / 「第一次」/ 素材)

> 2026-08-11。接 `docs/travel-moments-design.md`(三层架构 + 古法手账形态),
> 那份定了「是什么」,这份定「数据长什么样」。
> Schema 落在 `YanApp/src/lib/schema.journal.sql`(已并入 `schema.apply-all.sql`)。
>
> 三件一起定,是因为分三次改一定会打架:城市是素材的分格依据,
> 「第一次」要落在城市的时间序上,而素材的溯源指回采集层。先动任何一件,
> 另外两件都得跟着返工。

---

## 0. 一句话

**城市是容器,旅行是标签,「第一次」是透镜,素材是唯一真正缺的那张表。**

三样东西各自落在三层架构的哪一层,就是这次设计的全部内容:

| | 落在哪层 | 新增 | 丢了会怎样 |
|---|---|---|---|
| 城市容器 | 语义层 tag + 一张装饰表 | `journal_cities` | 能从 tag 重建,只丢册名和封面 |
| 「第一次」 | 语义层 tag | **零新表** | 不存在「丢一半」——它就是标签本身 |
| 素材 | 新的一层:资产库 | `journal_assets` | 页面上的元素全部落空 → 所以它按采集层保护 |

## 1. 城市容器

### 为什么容器是城市不是旅行

旅行册(`trip_notebooks`)是**轨道**那一侧:行程、账目、预算,有开始有结束。
手账是**漫游**那一侧。

一次旅行横跨几个城市,而一个城市会被去很多次。第二次去东京,翻开的应该是
**同一本册子**,上面留着上次的痕迹——「一个人在不同坐标下留下的自己的截面」,
坐标是城市,那次旅行只是其中一次。按旅行分册的话,同一个坐标的截面会被切碎在
三本不相干的册子里,而这恰恰是手账唯一不可替代的东西。

所以:`kind='city'` 是容器,`kind='trip'` 降格成普通标签(和 `place`/`mood` 同级)。
旅行册不动,它继续管它的行程和账。

### city_id 必须稳定,不能是名字

「东京」「Tokyo」「東京都」是一个地方。按名字存会分裂成三本册子,
而且换一次显示语言就全散架。

```
反查成功   city:{iso2}:{slug}     例 city:jp:tokyo
反查失败   city:?:{lat}_{lng}     按 0.1°(约 11km)取整的网格,resolved=false
```

反查走已有的 `lib/geocode.js`(Nominatim,免费无 key,自定义打卡已经在用)。

**反查失败照样收下这条记录**,先落在网格 id 上,以后补反查再合并——
拿不到数据 ≠ 数据是空的。这条在项目里犯过四次,每次都是丢用户数据;
这里如果写成「反查不到就不给存」,人在飞机上、在没信号的山里记的东西就全没了。

合并的规则(写代码时别自己发明):`resolved=false` 的网格册,反查成功后
把 `city_id` 改写成正式 id,同时把该 user 下所有 `kind='city'` 且 value 等于
旧网格 id 的 tag 一起改写。两步在同一个事务里,失败就整个不动。

### 表里只有两类东西

`journal_cities` 存的是:反查回来的字典信息(可重新拉)+ 用户改过的装饰
(`title` / `cover_asset_id` / `note`)。

整张表删掉,册子能从 `moment_tags` 的 city 标签重建,代价只是册名回退成反查名、
封面没了。**所以它是语义层,不是采集层**——这个判断决定了它的备份优先级和
出错时的处理方式(可以重建的东西,读失败时可以显示降级形态,不必阻塞)。

`journal_pages.city_id` 加了列但**不做外键**:它和 tag value 是同一种东西。
做成外键等于「城市册必须先存在,页才能存在」,而真实顺序常常是反的——
人先拼了一页,落地才知道这是哪。

## 2. 「第一次」

`docs/TODO.md` 已经把红线写死了:**「第一次」是这份数据的透镜,不是新数据模型。**
这次设计只是把那句话兑现成 schema——`kind='first'`,value 是用户自己写的那句话
(「第一次自己办入住」),**零新表**。

三条约束直接落在数据上,不靠界面自觉:

| 约束 | 数据上怎么保证 |
|---|---|
| 不预置清单 | 数据库里没有任何「第一次」的枚举表、没有 seed。value 是自由文本 |
| 不显示未完成 | 数据里根本不存在「未完成的第一次」这种行——发生过才有行 |
| 不统计数量 | **故意不建按 kind 计数的索引**,不加派生列。加了就一定会有人拿它做进度条 |

### 能算出来的那种「第一次」不落库

「第一次到东京」「第一次到日本」——这类是时间序的推论,由展示层当场算:

```
firstArrivalOf(moments, cityId)  →  该城最早的那条 moment(纯函数,可测)
```

落库就是把透镜焊死成模型:一旦有了 `is_first` 这种列,它就会被别的功能读,
然后开始需要维护、需要回填、需要在删记录时同步——一个本来只是「按时间排个序」
的事实变成了一份要对账的状态。

用户手写的那句 `first` tag 和推算出来的到达顺序是两回事,不要互相同步。

### 页面上那枚「初」印和 tag 无关

手账页上如果贴了一枚「初」的印,那是 `journal_items` 里的一个装饰元素,
和 `moment_tags` 的 `first` 没有绑定关系。记录是记录,拼贴是拼贴——
展示层不持有数据,反过来也一样:用户撕掉那枚印,不该删掉他记下的第一次。

## 3. 素材

三样里唯一真的缺表的。在此之前,抠好的图、扫好的票根只作为
`journal_items` 的一个字段(`asset_path`)存在,等于**「这只鸽子只属于这一页」**——
跨页复用、材料架、按城市翻素材,全都无从谈起。

`journal_assets` 把它提出来:一次入库,任意页复用。

```
kind   成品是什么(页面怎么渲染)  cutout / scan / photo / badge / paper / sticker
entry  从哪条口子进来的           extract / scan / upload / generated / official
```

**entry 是产品定义,不是实现细节。** 提取是去背景,扫描是留原物——一张票根
被当成抠图处理过一次,原物的毛边和纸质感就没了,而那正是票根的全部价值。
所以这两条路径必须在数据里分得开,不能事后靠 kind 猜。

`generated`(AI 纪念章)和 `official`(官方贴纸包)是后面两档,先占位不实现——
占位的成本是一行 check 约束,不占位的成本是将来改约束。

### 溯源不是所有权

`source_moment_id` / `source_photo_id` 指回采集层,`on delete set null`,**不是 cascade**。

原图/原扫描永远躺在 `moment_photos` 里不动,`journal_assets` 存的是派生出来的那张 PNG。
删素材不该动原图;原图万一被删,素材也该继续留在页面上——用户已经把它贴上去了,
那一页是他的作品,不该因为素材库的清理而塌掉。同理 `journal_items.asset_id`
也是 `set null`。

### city_id 让素材和城市咬合

素材天然属于某座城:在京都扫的票根、在伦敦抠的鸽子。材料架按 `city_id` 分格,
和城市册用**同一套 id**——这是三件一起定的直接好处,分开做的话这里几乎必然
会长出第二套城市标识。

### 旧列不删

`journal_items.asset_path` 保留(铁律:只加不删)。新代码一律写 `asset_id`,
读的时候 `asset_id` 优先、为空回退 `asset_path`。目前线上这两张表都还没有数据,
但规矩要从第一天就守住。

## 4. 本地存储(实现时按这个来)

手账是本地优先的:拼一页不能等网。四个新键,加的时候必须登记进
`src/lib/storage.js`,并且 `kind='user'` 的键**必须**在 `sync.js` 里有对应的
`run(域名)`,否则 `storage.test.mjs` 会红——那条测试守的就是「登录换账号丢数据」
那个 bug。

| 键 | kind | backfill 域 | 装什么 |
|---|---|---|---|
| `yan_moments_v1` | user | `moments` | 采集层:瞬间 + 照片本机路径 |
| `yan_moment_tags_v1` | user | `moments` | 语义层:city / first / trip / place… |
| `yan_journal_pages_v1` | user | `journal` | 页 + 页上的元素(items 内嵌在页里,页是原子单位) |
| `yan_journal_assets_v1` | user | `journal` | 素材库元数据(文件本身在 FileSystem) |

`journal_cities` 的本地副本放在 `yan_journal_pages_v1` 里一起走(它是装饰,
不值得单开一个键和一个补传域)。

文件落地顺序,**顺序不能反**:先写本机文件 → 再写元数据 → 上传是后台补。
反过来的话,元数据指向一个还不存在的文件,页面上就是一个永久的破图占位。

### 换账号:每条记录记一份 `remoteIds`

实现时撞上的坑,记在这儿免得以后有人「优化」掉:

本机 id 是自己生成的 uuid(时间前缀,`journalModel.newId()`),所以补传能用 upsert、
重试不会变成两份。但**不能拿同一个 id upsert 到新账号** —— 那一行属于旧 uid,
RLS 的 `using (auth.uid() = user_id)` 不成立,结果是**更新 0 行、不报错**。
静默什么都没发生,而登录只有这一次迁移机会。

所以每条记录带一份 `remoteIds = { [uid]: 远端 uuid }`:换账号 = 为新账号铸一批新
uuid、整份重传,照片→瞬间、素材→溯源、元素→素材 这些引用按同一张映射表改写
(`planMomentUpload` / `planJournalUpload`,纯函数,有测试)。
uuid 预先铸好再上传,所以重试用的是同一个 uuid,安全。

`nextState`(带着新铸的 id)必须**上传成功之后**才落盘——先落盘的话,
一次失败的补传会把 id 占掉,重试时误以为传过了。

### `storage_path` 必须可空(本地优先逼出来的)

草稿里 `moment_photos.storage_path` 是 `not null`。保持它的话,离线拍下的那条瞬间
在补传时**一行都插不进去**——而登录换账号只有一次机会,插不进去就是永久丢。
所以 `schema.journal.sql` 里放开了这个约束,新的 `journal_assets.storage_path`
也是可空的。放宽约束不是改名/删列/迁移数据,不违反采集层那条铁律。

同理:旧账号的 storage 路径**不能带着走**(`portablePath`)。文件在 `{旧 uid}/` 下,
新账号按 RLS 读不到,传一个必然 403 的路径就是页面上一张永久裂图——
打卡照片踩过这个坑。留空,本机文件还在,等重新上传。

## 5. 上线前必须先做掉的两件

1. **跑 `schema.apply-all.sql`。** 不确定线上库是不是最新的时候不要回忆跑过哪些,
   整段粘贴重跑。`word_progress` 和 `place_checkin.checked_in_at` 两次静默故障
   都是这么来的。
2. **`supabase.js` 的 `deleteAccount` 要加清 `moment-photos` 桶。**
   现在只清了 `checkin-photos`。数据库里的行会随 `auth.users` 级联删掉,
   Storage 里的文件不会,而 SQL 里删不了 `storage.objects`(报 42501,
   会让整个删号函数失败)。手账一上线,用户的照片和票根就都在那个桶里了——
   这是合规问题,不是清理问题。

## 5.5 材质、厚度、手写(2026-08-11 补)

**页面永不拍平。** `journal_items` 加了 `material` 和 `lift`(离纸面多高,单位是页宽千分比,
不是像素——换屏幕、换 300dpi 打印都不用改数据)。光影在渲染时才算。

这一条同时买下三件事,所以值得现在就定死:

| 想要的 | 靠什么 |
|---|---|
| 层次感(3D) | 贴纸浮 9、票根 3、胶带 1、印 0 —— 阴影的偏移和虚实跟着 lift 走 |
| 延展到本子外面 | 坐标不限制在页内,越界那半截的投影落在桌面上 |
| 可打印收藏 | 同一份数据换 300dpi 重渲,不是把屏幕图放大 |

所有拼贴 App 看起来是平的,原因就一个:给所有元素画了同一种柔和阴影。

**手写(`kind='ink'`)存矢量笔画,不存位图。** 一笔 = 一串 `[x, y, t, w]`:
相对坐标、毫秒时间戳、该点线宽(笔锋)。理由和「不拍平」同源——能 300dpi 重画、
能整笔擦除、能改颜色、一页几 KB。`t` 必须存:有它才能回放书写过程,
而它几乎不占空间,**现在不存以后补不回来**。

手指 / 键盘 / Pencil 的分工是产品决定,不是妥协:手指做涂鸦圈画箭头,
写字走键盘 + 手写体字库,真笔迹写字留给 iPad + Pencil。
硬让人用手指在 6 寸屏上写字,写出来他自己都不想看第二眼。

**字体:霞鹜文楷(LXGW WenKai),SIL OFL。** 判据是 OFL 而不是「免费商用」四个字——
后者常常只覆盖平面设计,嵌进 App 分发属于 embedding,要另外授权。
46490 字,中文 + 假名 + 西语重音和 `¿¡` 一套全覆盖,言不是只做日语,这一点很关键。
代价是 24MB:**不要打进包**,走远端按需下载(`expo-font` 支持从 URI 加载),
和内容包同一条管线。可爱体以后作为可选一档,字数不够时回退到文楷。

## 7. 这次明确不做

- 不给「第一次」建表、建计数、建清单
- 不把 `place_checkin` 迁到 moments(那是施工顺序第 8 步,和这次的三件事无关)
- 不动 `journal_items.kind` 的 check 约束(要加新 kind 时,先
  `drop constraint if exists journal_items_kind_check` 再重建,保持幂等)
- 不设计手账的 UI 数据流——画布怎么撤销重做是展示层的事,展示层不持有数据
