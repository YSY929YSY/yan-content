# 「言」· 产品介绍与困境(2026-08-16)

> 这份文档是给外部顾问看的。目标是**让建议落到具体的取舍上,而不是"要有清晰的用户路径"这类正确但没用的话**。
> 所以下面所有数字都是从代码和数据里实测的,不是印象。

## 0. 一句话

**「言」是一个给中文母语者的日语学习 + 旅行记录 App。** iOS 已上架 v1.1.0,**没有做任何宣发,没有用户**。个人开发,一个人。

## 1. 现在有什么

### 1.1 三个一级页签

| 页签 | 内容 |
|---|---|
| **首页** | 汇总:今天要复习几个词、进度 |
| **出发 · 地铁** | 五个子页:出发前 / **地铁冒险** / 五十音 / 词书 / 复习 |
| **世界打卡** | 地点打卡、旅迹(按到访日期连线)、手账、分账本 |

### 1.2 学习侧模块

- **五十音**:清音 20 行 / 浊音 5 / 拗音 11 / 外来音 4 / 特殊音。完整。
- **词书**:8005 条,按 JLPT 分 N5–N1,Leitner 间隔复习(SRS)。
- **场景卡**:6 个场景(地铁交通、餐厅、便利店、住宿、问路、应急),每个带目标清单、零基础起步提示、文化注释。
- **地铁冒险**:东京地铁逐站关卡,每站一关,通关解锁下一站。带铁道史/换乘/IC 卡边界等长篇文化解说。
- **文化融合**:一个词根串起中/日/英/西四种语言(例:火山 / かざん / volcano / volcán ← 罗马火神 Vulcan)。
- **文化注释**:6 条独立的文化点(如「すみません 万能词」)。

### 1.3 旅行侧模块

- **世界打卡**:43 个预置地点(火山/雪山/河湖/咖啡…),每个地点绑一句当地语言的实用句。
- **旅迹**:按**实际到访日期**(不是记录日期)把去过的地方连成线。
- **手账**:自由画布,照片/票根/词纸条/印章/胶带贴在纸上,可拖可转可溢出纸外。**正在重构,数据层和交互层刚完成,未在真机验证。**
- **分账本**:多人共享,按币种分组结算,不做汇率换算。

### 1.4 已经建好但**没有上线**的资产

- **音调(アクセント型)数据 7510 条**,三源交叉验证过(kanjium × zh.wiktionary × UniDic),CC-BY-SA。
  ⚠️ 仍在 `staging/`,**一条都没进线上词库**。线上 8005 条词的音调字段是空的。

## 2. 困境(这份文档的重点)

### 2.1 核心困境:开发者自己答不上"怎么用它学日语"

原话:

> 「我自己设计其实我都不知道我要怎么去学习日语,如果单靠言还是有一种无论如何也学不好日语的感觉,感觉很混乱很复杂。」

模块单看都不差,但**没有一条主线**。任何时刻用户打开 App,得不到"我今天该干什么"的答案。
对照多邻国:它的优势不是课程编得好,是**任何时刻只有一个下一步**。

### 2.2 内容库存和产品主张是**反着的**(实测)

这是最尖锐的一条。逐条实测:

| 指标 | 实测 | 含义 |
|---|---|---|
| 词库总量 | 8005 | 够用 |
| **JLPT 分布** | N5 **724** / N4 631 / N3 1712 / N2 1774 / **N1 3164** | **40% 是 N1** —— 初学者永远用不到的那头最厚 |
| **内容状态** | `verified` **2 条** / `zh_drafted` 6642 / `draft` 716 / `candidate` 645 | **人工核过的只有 2 条** |
| 有完整例句 | 4400 / 8005(55%) | 近一半的词没有例句 |
| **有音调** | **0 / 8005** | 做好的 7510 条卡在 staging |
| **`yanFeatures` 覆盖** | **663 / 8005(8%)** | 见下 |
| 其中 `kanji_anchor` | **563 条** | **产品最独特的资产,只覆盖 7%** |
| **场景标签** | 7985 / 8005 都是 `daily` | 只有约 **170 条**有真实场景;场景标签**等于没用** |

**结论:库存最厚的地方(N1)是用户最晚才需要的;库存最薄的地方(汉字锚点、场景、音调)恰好是这个产品唯一不可替代的地方。**

### 2.3 一个已经潜伏在数据里、但没被当成主线的东西

代码里已经存在一套分类,**但只覆盖了 8% 的词**:

```
汉字直读 (kanji_anchor)   563   中文母语者一眼就懂的词
陷阱字   (lookalike)       35   长得像但意思不同(手紙=信,不是手纸)
音变     (sound_change)   111   同一个汉字的音读/训读
英语跳板 (loanword)        72   外来语
拉丁词根 (etymology_image) 65
口语/书面(spoken_written)  35
```

这套分类正是「中文母语者学日语」区别于「英语母语者学日语」的全部要害,但它现在只是词卡上的一个标签,**不是学习路径**。

### 2.4 出海的真实成本(实测)

- 界面中文字符串:**App.js 718 条 + src/ 1305 条 ≈ 2000 条**
- i18n 基建:**没有**。一个 `t()` 都没有,全部硬编码
- 词库已有 `meaning_zh` + `meaning_en` 两个字段(这层没债)
- 词条 id 是罗马字(`n5_en`),不含中文(这层也没债)

**所以出海的成本不在翻译词库,在那 2000 条界面文案,而且还在增加。**

## 3. 数据结构(给出具体建议时请对着这个)

### 3.1 词条

```jsonc
{
  "word": "～円", "reading": "～えん",
  "level": "N5", "levels": ["N5"],
  "pos": "量词",
  "meaning_zh": "……日元", "meaning_en": "Yen",
  "status": "draft",              // draft | zh_drafted | candidate | verified
  "tags": { "scene": ["daily","convenience"], "type": ["grammar"], "memory": [] },
  "coreChunk": "千円を払う",
  "exampleJp": "全部で三千円です。",
  "exampleZh": "一共三千日元。",
  "exampleRoma": "Zenbu de san senen desu.",
  "id": "n5_en",                  // 唯一,8005 条 0 重复 0 缺失
  "yanFeatures": ["kanji_anchor"],
  "jmdictSeq": 1234560,
  "conceptCluster": "money"
}
```

- **复习进度的键是 `词-读音` 拼出来的字符串**,不是 id(历史原因,已有用户数据)。
  两套键并存,`keyAliases.js` 里有 292 行别名表处理合并过的词条。
- 音调数据在 `staging/pitch-accent.json`,结构是 `{ "词-读音": [型号] }`,7510 条,未合并。

### 3.2 场景卡

```jsonc
{
  "id": "subway", "label": "地铁 & 交通", "desc": "买票 · 换乘 · 出口",
  "ready": true,
```

### 3.3 手账(刚重构完,是目前设计最完整的一块)

```ts
// 一切都是「贴在纸上的一个东西」,共用同一个基类
type JournalItem = {
  id: string;
  type: 'photo'|'scan'|'cutout'|'stub'|'wordSlip'|'stamp'|'sticker'|'text'|'tape';
  x: number; y: number;      // 元素中心,页面单位,可为负、可超出纸面
  w: number; h: number;      // 落地尺寸
  rotation: number;          // 必填,不是可选装饰
  scale: number;             // 0.3 ~ 3
  zIndex: number;            // 必填
  material: 'paper'|'photo'|'tape'|'sticker'|'vellum'|'scan'|'ink';
  lift: number;              // 离纸面高度,阴影由它算
  payload: unknown;          // 按 type 分
  createdAt: number;
};

type JournalPage = {
  id: string;
  bookId: string | null;     // 手动册子;空 = 散页
  cityId: string | null;     // 按城市自动分格(与册子并存)
  dateISO: string | null;
  items: JournalItem[];
  strokes: Stroke[];         // 笔迹是页级的,不是一种 item
  paper: 'plain-cream'|'dot-cream'|'grid-ivory'|'kraft-bag';
};

type Stroke = {              // 存点数组,不存图片 —— 能改色、能回放、能按任意分辨率重绘
  id: string; color: string;
  tool: 'pen' | 'eraser';
  points: { x: number; y: number; p: number; t: number }[];  // p=压力, t=毫秒
};

// 词纸条 —— 词和手账的接口
type WordSlipPayload = {
  wordId: string;            // 指向词库 id
  word: string; reading: string;   // 贴上去那一刻的字面快照
  note: string;              // 用户自己写的,不是词卡释义
};
```

设计原则一句话:**词卡是词的定义,手账是词的传记。**

### 3.4 后端(Supabase / Postgres,全部开 RLS)

```
词      word_progress(box, due_at, reps, lapses, last_seen_at, status)
打卡    user_places, place_checkin, travel_checkins, travel_photos

```

本地优先 + 登录后回填。硬规矩:**「拿不到数据 ≠ 数据是空的」**(这个项目为此丢过四次用户数据)。

### 3.5 技术栈

React Native / Expo SDK 54,Skia(手账渲染),gesture-handler + reanimated(手势),
Supabase(Postgres + RLS + Storage)。测试只覆盖纯函数,400 条,`node --test`。
**UI 与 hook 零覆盖**——这是刻意的,但每一个丢过数据的 bug 都出在这层。

## 4. 不可动的前提(请在这些约束内给建议)

1. **地铁冒险和文化融合不能砍。** 这是开发者明确的决定,不在评估范围内。
   如果你的方案里它们没有位置,请调整方案,而不是建议砍掉它们。
2. **五十音是起点**,这点没有争议。
3. **远期要出海,以英语为底色**(因为用户基数最大)。这是开发者的既定目标。
4. 个人开发,一个人,没有内容团队。**任何需要大规模人工审校的方案都要说明谁来做。**
5. 开发者本人**不懂日语**。所以内容策略必须建立在「有没有权威来源可核对」上,不能建立在「自己能审」上。

## 5. 想请教的问题

### Q1(最重要)**主线应该是什么?**

现在是十个模块并列。需要一条"任何时刻只有一个下一步"的主线,**而且它必须能容纳地铁冒险和文化融合**(见约束 1)。

一个候选方案是:**把定位从「教你日语」改成「把你已经会的汉字,变成你能说出口的话」**——
理由是中文母语者的难点不是词义而是读音(認識「準備」但不会念 じゅんび),
典型症状是"看得懂、听不懂、说不出"。这条路线会让 `kanji_anchor` 从标签升级成主线。

**请评估这个方案,或提出更好的。** 如果采纳,请具体说:8005 条词怎么重新组织?N1 那 3164 条怎么办?

### Q2 **中文母语者定位 vs 英语出海,这个矛盾怎么解?**

这是这份文档里最大的张力,开发者和上一位顾问意见不同,想听第三方判断:

- 「你已经认识 2000 个日语单词了,只是还不会读」这个钩子,**对英语母语者一句都不成立**。
  对中文母语者,汉字是**起跑线**;对英语母语者,汉字是**最大的墙**。同一套教学法面对两群人是反的。
- 上一位顾问的意见:**繁中(台/港)是同一个产品**(共享汉字优势,转换成本低,只需注意用 OpenCC 的 `s2twp` 做词汇级转换而非字形转换);
  **英文版是另一个产品**,不能靠翻译得到,真要做应该以旅行记录/手账为主体、语言学习为轻层。
- 开发者的意见:**远期仍然要以英语为底色,因为用户基数最大**。

**请判断:是否存在一个方案,既保住中文母语者的结构优势,又能扩展到英语基底?还是必须二选一?**
如果必须选,请给出理由和时间点(什么时候切、切之前该做什么)。

### Q3 **内容优先级怎么排?**

现在的实测状态是:N1 有 3164 条但 `verified` 只有 2 条,`kanji_anchor` 只有 563 条,场景标签形同虚设,音调 7510 条卡在 staging。

一个人、没有内容团队、本人不懂日语。**下一个月应该先补哪一样?**

### Q4 **出圈的钩子**

候选:第一屏给一句日语不给翻译 → 用户发现自己读懂了 → 「你已经认识约 2000 个日语单词,只是还不会读」。
可截图、可分享,而且说的是真话。

**请评估这个钩子,或提出更好的。** 也请指出它的风险(例如:是否会让用户高估自己、之后遇到语法和听力时挫败感更强)。

### Q5 **模型层**

目前 LLM 调用点只有一个(行程解析,Supabase Edge Function)。
有建议说要建 model router 按延迟/成本分档。上一位顾问认为一个调用点建路由是过度设计,
主张只做一个 `llm.ts` 接缝(对外 `run(task, context)`,模型 id 和 prompt 关在里面,记录 task/延迟/token)。

**请判断哪个更合适,以及在什么规模下应该升级成真正的 router。**
