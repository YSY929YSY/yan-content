### A2 的执行条件 —— ⚠️ 2026-08-17 更正

**此前的判断是错的。** 顾问意见和本记录都写过「音调表的键是 `词-读音`,
而复习进度的键也是 `词-读音`,这是丢过四次数据的那个键」。实测:

```
staging/pitch-accent.json 的键是**词条 id**(n5_au、n5_ao…),不是 词-读音
```

所以这是一次 **id → id 的 join,不碰 `词-读音`,完全不碰复习进度**。
它给词条加一个字段,不改任何键。风险等级远低于此前判断。

⚠️ 错误来源:CC 在顾问文档里写了「结构是 `{ "词-读音": [型号] }`」——
凭部分样本写的,没核文件。四位顾问据此都加了 dry-run 警告。

dry-run 仍然要跑,但**理由变了**:不是防丢数据,是看能对上多少。
实测结果(`tools/pitch-dry-run.py`):

```
id 唯一性     8005/8005 有 id,0 重复,0 孤儿,0 形状错
matched       6662 (83.2%)  单一型,直接可用
matched_multi  848 (10.6%)  多个型,取第一个 —— ⚠️ 这条规则无源可核
word_no_pitch  495 ( 6.2%)  合入后音调仍为空
合入后覆盖率   7510/8005 = 93.8%
主线池影响     563 条里 46 条无音调,其中 31 条是接尾词(本就押后),真正影响 15 条
```

下面这段是**此前**的判断,保留作对照:

> **合并脚本必须先跑 dry-run,输出分类计数 + 每类样本,人看过再写。**
> GPT 建议的六类比三类好:`exact_match / alias_match / ambiguous_match / multi_accent / unmatched_pitch / word_without_pitch`
> 且**这次只加 pitch 字段,不顺手迁 progress key**。一次迁移只解决一个问题。

## E. 两条改变判断的事实

### E1 关于「一个人 / 不懂日语」这条约束的表述

顾问文档的约束 4、5 写成了「一个人」「本人不懂日语」,**所以五份报告全在把它念回来**。这个措辞是 CC 写的,不准确,已弃用。

**正确的分界不是「有没有懂日语的人」,是「这条声明有没有可核对的源」——这是声明的属性,不是人的属性:**

| 声明类型 | 有源吗 | 谁能验 |
|---|---|---|
| 读音、音调、词义、JMdict 释义 | ✅ | 对着源查即可 |
| 「这句例句自然吗」「日本人真会这么说吗」 | ❌ | 需母语 + 受训,且未必对 |

对第二类,解法**不是「找个人来审」**,是**别做没有源的声明**,或明确标注为生成内容。

### E2 ⭐ 开发者本人就是目标用户,而且在同时学日语和西语

原话:「我就是在自己想要学习日语和西语的时候碰到了需求和困境呀」

三个后果:

1. **「我自己都不知道该怎么学」不是设计缺陷的自述,是最高质量的用户反馈。** 目标用户打开 App 不知道下一步该干什么——可以直接采信,不必再找五个陌生人验证这一条。
2. **「跨语言同时学」是现在时,不是远期规划。** 文化融合那条「火山/かざん/volcano/volcán」是开发者自己的学习需求漏进了产品。⚠️ 但数据上它是 4 条 + 0 条 `conceptCluster`(B4)——**要押它就是从零开始**。
3. **三节点原型可以先给自己用。** 不能替代陌生人测试,但「我知道下一步该干什么了吗」今晚就能答。
