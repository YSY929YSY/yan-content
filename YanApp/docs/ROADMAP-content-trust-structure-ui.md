## 0. 先说结论

现在不应该继续追求“把 8005 个词的词源全部证明清楚”，也不应该先做一次覆盖全仓库的大重构。

正确顺序是：

1. **先建立内容发布契约**：明确区分“可查”“可学”“可展示深度内容”。
2. **立即堵住错误流入学习与复习的入口**：机器稿不能因为例句齐全就自动成为正式学习内容。
3. **建立来源台账和字段级证据**：词典、教材、GitHub、语料库各司其职，不再混成一个“参考过”的状态。
4. **再做边界清晰的小步重构**：把内容规则从 `App.js` 中抽成唯一入口，然后逐屏拆文件。
5. **最后继续生产词源和特色内容**：词源是稀疏的高价值增强，不是全词库的准入门槛。

当前真正卡住团队的并不是“找不到绝对可靠的来源”，而是下面四件事被揉成了一件事：

- 一个词是不是客观存在、读音和词性是什么；
- 中文释义能不能发布；
- 这个词能不能进入学习与间隔复习；
- 这个词有没有值得展示的词源、汉字锚、故事或文化连接。

这四件事必须使用不同标准。只要继续用一个 `status` 或“例句齐不齐”同时回答四个问题，团队就会一直困在真实性里。

代码中的核心错误在 `App.js`：

```js
const isDraftedWord = (w) => !(w?.exampleJp && w?.exampleZh && w?.exampleRoma);
```

这段逻辑回答的是“例句字段是否齐全”，却被拿来回答“词条是否可正式学习”。按跨等级去重后，目前有 3037 个 `zh_drafted` 词条会因此被自动放进正式词书口径（按 N3/N2/N1 视图分别计数为 1365、819、993，同一词可能跨级，不能直接相加）。字段完整不是人工核验，也不是发布授权。

同时，五本词书现在全部 `available: true`。搜索详情还允许对起草词直接评分，评分后它会进入 SRS。结果是：产品嘴上说“起草稿只当词典翻”，行为上却允许它变成学习内容。

### 1.2 学习与复习

现有 SRS 和进度 Context 是有价值的基础，不应该推倒重做。真正的问题是“什么有资格进入 SRS”没有被建模。

当前混合复习会把以下来源归一：词、深卡、地点、场景、地铁、词场。这一方向是对的，但队列会在到期内容不足 10 条时补入用户从未主动遇见过的深内容。于是“复习”混入了“首次教学”。此外，地点卡可以不经过真实打卡直接进入候选。

需要新增的不是第二套复习算法，而是内容引入记录：

```ts
type IntroducedFrom =
  | 'word_batch'
  | 'manual_save'
  | 'scene'
  | 'place_checkin'
  | 'subway'
  | 'word_card';

type Introduction = {
  introducedAt: string;
  introducedFrom: IntroducedFrom;
  originId?: string;
};
```

规则：**只有用户已经遇见、主动保存或完成过的内容才能进入“复习”；未引入内容只能出现在“探索/新内容”。**

### 1.3 场景、趣味性与地铁

- 6 个 ready 场景，共 69 句：地铁 14、餐厅 8、便利店 10、酒店 12、问路 12、紧急 13。
- 首页叫“出发前七天”，但数据和界面没有七天节奏、天数进度或每日目标。
- 页面叫“核心句型”，实际更接近场景短句集合。
- 首页“场景实战”写着“地铁 · 餐厅 · 酒店”，点击却进入地铁冒险，承诺范围与落点不同。
- 地铁有 5 站，每站只有 3–4 句；站内 `words` 与 `quiz` 都是 0。它目前更像换皮分页，而不是冒险或练习闭环。
- `culturalFusion` 只有 4 项，首页每次从第 0 项开始。它是装饰性轮播，不是会产生期待的内容机制。

“趣味性不足”不是因为动画不够，而是因为用户的动作没有改变世界：学完一句没有解锁新的可见结果，去过一个地方没有产生专属学习包，地铁通关没有形成可带走的能力证明，手账也没有自动承接这些经历。

### 1.4 世界打卡

- 43 个精选地点，15 个是火山，主题分布偏斜。
- 地点语言卡的完整度不一致，短语数量也不一致。
- `amazon` 定位为巴西，却使用 `es-ES` 与西班牙语；在巴西场景下应优先考虑葡萄牙语 `pt-BR`。
- “亚马逊雨林生产全球 20% 氧气”是广泛传播但不宜继续作为事实陈述的说法，应删除或改写。
- “亚马逊河没有一座桥”等文化彩蛋也应允许表达限定条件和来源，而不是把吸引人的说法直接写成绝对事实。
- 目前“精选地点”和“我的真实足迹”容易在叙事上混在一起。首页把所有深内容到期项说成“来自你走过的地方”，但深卡、场景、地铁并不必然来自用户去过的地方。

世界模块最有价值的方向不是继续填更多景点，而是建立：**地点 → 当地一句话 → 用户真实到访/想去 → 复习 → 手账回忆** 的闭环。

### 1.5 手账

新版手账有明确的画布、元素、层级与纸张结构，方向可保留，但现在仍是开发原型：

- 生产入口受 `__DEV__` 限制。
- `JournalScreen.tsx` 只读取 `pages[0]`。
- 每次保存写入 `{ pages: [stamped] }`，尚未形成多页/多册产品。
- “注文”词条与 `KYOTO / 2026` 印章是硬编码演示内容，不是用户上下文。
- `storage.js` 把 `journalPagesV2` 登记为需要 journal backfill；但 `journalSync.js` 的 `backfillJournal()` 经由 `journalStore.readAll()` 读取的是 v1 `journalPages`，不会读取 v2。登记表表达的承诺和真实同步路径不一致。
- v2 与旧版 `JournalDevScreen.js`、`JournalPage.js`、`journalRender.js`、`journalGesture.js` 同时存在。旧代码不是全都能立刻删：`journalMigrate.ts` 明确承担未来迁移职责。

这是 P0 数据安全问题，不只是代码洁癖问题。对用户作品来说，“能不能跨登录保住”优先于“再加一种贴纸”。

### 1.6 旅行小本子与分账

`src/features/travel/TripNotebook.js` 约 3345 行，同时承担：

- 多本旅行册与行程编辑；
- 订单截图导入/OCR 结果处理；
- 旅行短语包；
- 汇率；
- 本地账本与共享账本；
- 费用编辑、分类、成员、预算、结算与同步。

产品上“小本子”和“分账”可以互相靠近，但数据上已经是两个独立对象；代码却仍在一个大组件里。当前还有两个 Emoji 浮动入口（📓/🧮），可发现性和可访问性都弱。共享账本缺少明确的“退出账本”能力。

应该先拆状态所有权与业务域，再调整视觉；不要先搬 StyleSheet 或做机械式 TypeScript 化。

### 1.7 基础设施与冗余

- `App.js` 约 6335 行，是目前最大的迭代风险。
- `TripNotebook.js` 约 3345 行，是第二个风险点。
- `contentCache.js` 只做 `JSON.parse`，远端 JSON 结构错误仍可能覆盖有效缓存并进入 App。
- `scripts/validate-content.js` 只认可 `snow/volcano/water/cafe`，不认识目前更多地点类型，也不认识 `wordBank`、`wordCards` 等主要内容；当前运行会产生大量假错误/噪声，已经不能担当发布闸门。
- `MAP_TYPES` 未使用。
- `searchPlace` 被导入但未使用，实际使用的是 `searchPlaceDetailed`。
- `WORD_CARDS_BUILTIN` 在 `App.js` 中重复维护 8 张远端内容卡，作为 fallback 有用途，但约 660 行的人工副本存在严重漂移风险。
- 根文档与交接文档中的词数、测试数、功能状态已多次漂移。事实不应继续手写在多个 Markdown 中。

## 2. 产品应采用的“三层内容契约”

### 2.1 第一层：Dictionary（可查）

用途：全库搜索、帮助用户确认一个词的写法、读音、基本义与词性。

最低要求：

- 稳定 ID；
- 日文表记与读音经过词典源匹配；
- 词性与义项来自可追溯来源；
- 中文可以是内部翻译稿，但必须标明审核状态；
- 不要求例句、词源、词场或故事；
- 默认不能因为“被搜索到”就进入 SRS。

### 2.2 第二层：Learning（可学）

用途：今日新词、正式词书、评分与间隔复习。

最低要求：

- 已满足 Dictionary；
- 中文核心义人工核对；
- 义项范围与例句中的具体意思对齐；
- 例句日文自然、中文对应、读音/罗马音可复算；
- 有明确的发布开关；
- 由产品路径“介绍给用户”或用户主动保存后才能进入 SRS。

### 2.3 第三层：Editorial（言的深度内容）

用途：汉字锚、陷阱、词源、外来语连接、词场、文化联动、深卡。

最低要求：

- 所有事实性主张有字段级证据；
- 解释、联想和事实明确区分；
- 不确定或有争议时可以不展示；
- 只做最值得做的词，不设全库覆盖 KPI。

建议新增显式发布字段，而不是从字段是否为空推断：

```json
{
  "publication": {
    "dictionary": "published",
    "learning": "reviewed",
    "editorial": "none"
  }
}
```

建议状态枚举：

- `blocked`：已知错误或授权问题，任何入口都不展示；
- `draft`：内部工作稿；
- `reviewed`：已按本层标准核过；
- `published`：允许在对应产品面展示。

如果觉得三层枚举过重，第一期可以先加两个布尔开关：

```json
{
  "publication": {
    "dictionary": true,
    "learning": false
  }
}
```

但不要继续使用 `status !== 'zh_drafted'` 或例句完整度作为发布判断。

### 2.4 第一批迁移建议

不要一次人工重审 8005 条。第一批迁移只做确定性映射：

1. 全部词先 `dictionary: true`，前提是通过 JMdict 表记/读音 join 与最基本结构校验；join 失败的设为 false 并进异常清单。
2. N5/N4 不要因“看起来精修”整体自动设为 `learning: true`；先生成待核清单，再由人确认批次发布。
3. N3/N2/N1 第一阶段统一 `learning: false`，仍可全库搜索。
4. 8 张深卡单独核验后标 `editorial: published`；没有深卡的词不是“不完整”。
5. 旧 `status` 暂时保留用于追踪生产批次，但不再直接控制 UI。

## 3. 修改优先级与原因

### P0：发布前必须解决——信任与用户数据安全

#### P0-1 用显式发布契约替换 `isDraftedWord`

**原因**：现在的逻辑会把 3037 个去重后的 `zh_drafted` 高等级词条自动当成正式学习内容。这是内容信任的根漏洞。

**建议修改**：

- 新建 `src/content/publication.ts`；
- 导出 `isDictionaryEntry(word)`、`isLearnableWord(word)`、`hasEditorialDepth(word)`；
- 词书列表、今日批次、搜索详情、复习候选全部调用这些 selector；
- 保留 `hasCompleteExample(word)`，但它只表示字段完整度；
- 搜索中的不可学词隐藏评分按钮，改为“加入我的词”或“此词条尚未开放学习”；
- 如果实现“加入我的词”，它代表用户主动承担草稿风险，应进入独立 `manual_save` 路径，并在详情中说明内容成熟度。

**验收**：

- N3/N2/N1 默认不产生今日学习批次；
- 搜索起草词不能直接调用 `grade()`；
- 补齐例句不会自动改变发布状态；
- 单测覆盖完整例句但 `learning: false` 的词仍不可学。

#### P0-2 给远端内容增加运行时 schema 校验

**原因**：当前远端内容只要是合法 JSON 就会被缓存和使用。一个字段类型错误或缺顶层数组的推送，可能让所有已安装 App 同时出错。

**建议修改**：

- 新建 `src/content/schema.ts` 与 `src/content/contentValidation.ts`；
- 先做“最小可运行 schema”，不要一开始验证每个可选字段；
- 校验失败时：不写新缓存、不替换当前内存内容、继续使用上一份缓存或 bundled fallback；
- 返回结构化错误码和路径，开发环境打印摘要；
- 把内容版本、schema 版本、校验结果加入 release report；
- 更新或替换 `scripts/validate-content.js`，让发布前与 App 运行时共用同一组规则，避免两套标准。

**验收**：

- 合法 JSON 但 `wordBank` 为对象时不会覆盖缓存；
- 缺 `scenes` 或词条 ID 重复时能得到可读报告；
- 模拟坏远端包，App 仍使用最近一份有效内容；
- `npm test` 与 `npm run typecheck` 通过。

#### P0-3 修复手账 v2 的备份承诺

**原因**：`journalPagesV2` 登记为参与补传，但真实 backfill 读取 v1。用户会以为登录后作品被保护，实际上 v2 页可能没有上传。

**建议修改前先做产品决定**：

- 方案 A：v2 仍是开发原型。移除生产入口与“会同步”的承诺，登记为 device/prototype，等数据模型完成后再开放。
- 方案 B：v2 准备成为正式版。实现 v2 的多页读写、迁移和 backfill，并增加登录迁移测试。

推荐 B，但要先完成多页模型。无论选哪种，都不能保持“登记说会同步、代码实际上不同步”。

**验收**：

- 新建两页、重启、两页仍在；
- 匿名状态创建 → Apple 登录 → 云端能找到 v2 页；
- 失败重试不会产生重复页；
- v1 数据仍可迁移且不会被覆盖。

#### P0-4 修正文案与事实错误

**原因**：这类错误小但直接伤害可信度，比缺功能更严重。

**首批清单**：

- 巴西亚马逊地点的语言改为合适的葡萄牙语场景，或把地点范围明确改到西语国家；
- 删除/重写“亚马逊雨林占全球氧气生产 20%”；
- 首页“来自你走过的地方”按真实 source 分别表述；
- “场景实战”要么进入场景选择页，要么文案只写地铁；
- “出发前七天”在没有七日结构前改成“出发常用句/旅行急救句”，或者真正实现 7 天计划；
- “核心句型”若没有句型抽象与替换槽，改成“场景必备句”。

#### P0-5 区分“新内容”和“复习内容”

**原因**：用户打开复习时不应被暗中塞入从未学过的地点或深卡。这个问题会破坏学习模型的可理解性。

**建议修改**：

- 记录 `introducedAt` 与 `introducedFrom`；
- Review 队列只取已引入且到期的单元；
- 未引入内容进入“探索”或“今日新内容”；
- 地点卡只有打卡、主动收藏或明确点“学习这句话”后才引入；
- 首页统计按来源准确展示，如“2 条来自场景练习，1 条来自足迹”。

### P1：紧接着做——建立可持续迭代边界

#### P1-1 建立内容领域层

建议目录：

```text
src/content/
  schema.ts
  publication.ts
  selectors.ts
  contentValidation.ts
  contentStats.ts
  sourceRegistry.ts
```

职责：

- `schema.ts`：内容包和关键实体类型；
- `publication.ts`：三层发布判断，唯一真相来源；
- `selectors.ts`：按级别、场景、状态、来源取内容；
- `contentValidation.ts`：运行时与发布前共用的校验；
- `contentStats.ts`：自动统计词数、覆盖率、异常数；
- `sourceRegistry.ts`：来源 ID、版本、许可和归属文本。

这一步是代码重构的起点，因为它先把“决定产品行为的规则”抽出来，而不是为了文件好看而搬代码。

#### P1-2 从 `App.js` 按屏幕逐个抽离

建议顺序：

1. `WordBookShelfScreen`、`WordBankScreen`、词详情；
2. `HomeScreen`；
3. `LearnScreen` 与场景流；
4. `SubwayScreen`；
5. `WorldScreen`；
6. 最后才动路由装配。

每次只抽一个屏幕：行为、文案、颜色、导航 state 都不改。抽完运行测试和真机冒烟，再进入下一屏。`App.js` 最终只保留 bootstrap、provider、顶层路由和少量跨屏装配。

禁止在这轮顺手做：

- 全项目改 TypeScript；
- 全局重命名；
- 替换色板；
- 同一提交既拆文件又改产品逻辑；
- 为了减少行数把多个领域塞进一个新的 `screens.js`。

#### P1-3 拆分旅行小本子与分账

建议目录：

```text
src/features/travel/notebook/
  TripNotebookScreen.js
  useTripBooks.js
  TripList.js
  ItineraryEditor.js
  OrderImport.js
  TravelPhrasePack.js

src/features/ledger/
  LedgerScreen.js
  useLedgers.js
  ExpenseEditor.js
  BudgetPanel.js
  SettlementPanel.js
  LedgerMembers.js
```

拆分次序：

1. 先抽纯函数和数据适配；
2. 再抽 hooks，明确谁拥有旅行册 state、谁拥有账本 state；
3. 再拆 UI 区块；
4. 最后把两个 Emoji FAB 改成有文字的明确入口；
5. 增加共享账本“退出”与权限边界。

不要把账本重新挂成旅行册子对象。用户只分账不做行程，是合理主路径。

#### P1-4 把动态事实从 Markdown 搬进自动报告

建立 `scripts/report-content-stats.*`，输出：

- 总词数和各等级去重数；
- publication 三层数量；
- 例句、coreChunk、来源、深卡、词场覆盖率；
- 未找到来源、join 冲突、重复 ID、跨等级重复；
- 场景/地点/语言分布；
- release blocker 与 warning。

文档只描述规则，不再手写“目前 8298 条/测试 212 个”这类会漂移的事实。CI 或 release script 每次生成报告。

### P2：边界稳定后做——把产品从“功能集合”变成闭环

#### P2-1 先做 30 个标杆词，不做 8005 个词源

选择标准：

- 旅行高频；
- 汉字锚对中文用户真的有帮助；
- 有容易误解的中日差异；
- 有可靠且有趣的来源故事；
- 能在真实场景中说出口。

每个标杆词应走完整链路：汉字锚 → 核心义 → 一句真实场景 → 听 → 说/替换 → 进入复习 → 可落入手账。若 30 个词的闭环不让人想继续，做 3000 个词源也不会改善产品。

#### P2-2 重做地铁的“冒险”定义

每站至少包含：

- 一个明确任务，例如“找到正确站台”；
- 2–4 个输入句；
- 一次听辨或情境选择；
- 一次主动说/选正确表达；
- 通关后的可见奖励：路线点亮、印章、手账票根或能力标签；
- 通关内容记录为 `introducedFrom: subway`，后续进入复习。

如果暂时没有这些，宁可叫“地铁五站练习”，不要靠“冒险”承担未实现的乐趣。

#### P2-3 世界打卡与手账打通

建议闭环：

```text
想去/去过一个地点
  → 学当地一句真正能用的话
  → 主动保存或现场打卡
  → 生成地点印章/一句话卡
  → 进入手账素材库
  → 到期后以该地点为上下文复习
```

精选地点只负责启发；用户自建地点才是个人世界。地点类别要围绕用户动机扩展（城市生活、自然、交通、食物、人与瞬间），不应继续由“火山数量”主导。

#### P2-4 完成手账最小产品

最小闭环不是更多材质，而是：

- 新建册/页；
- 页面列表与切换；
- 从一次打卡、一个已学词、一张照片创建素材；
- 自动保存并显示保存状态；
- 重新打开仍能找到；
- 登录后可恢复；
- 导出一张图片。

“注文”和“KYOTO”应变成从用户最近学习/最近地点生成的动态示例。

### P3：保留但不要提前开发

以下文件/概念目前看似未使用，但服务于明确的后续能力，不应简单按死代码删除：

- `journalMigrate.ts` 与相关 v1/v2 迁移逻辑；
- SQL schema 与 apply-all 入口；
- `wordIds.manifest.txt`、`keyAliases.js`：保护长期学习进度键；
- staging 中的来源证据、join 报告、候选报告；
- `moments`、`cities`、assets 等手账采集层结构；
- preview 数据，但应明确标成 development-only，不能混入生产统计。

## 4. 来源到底怎么解决：教材、GitHub、词典各自能做什么

### 4.1 先建立“来源角色”，不要问“哪个来源包办一切”

| 来源类型 | 适合做什么 | 不适合做什么 | 发布注意 |
|---|---|---|---|
| JMdict/EDRDG | 日文表记、读音、词性、义项骨架、常用标记、sense 限制 | 直接提供高质量中文、旅行场景、品牌化解释 | 保留 entry ID、版本与归属；派生分发须遵循原许可 |
| SudachiDict/UniDic | 分词、原形、读音、词性、活用与例句机械校验 | 替代面向学习者的释义；证明词源故事 | SudachiDict 标注 Apache-2.0，但其包含上游资源，仍需保留完整 NOTICE/许可链 |
| Tatoeba | 寻找例句候选、真实表达参考、部分可归属的句对 | 未经审核直接批量成为正式例句；用数量代替自然度 | 文本通常有 CC BY 要求，必须保留句子 ID/作者/许可；质量需要二次审核 |
| KanjiVG | 汉字笔顺与结构视觉素材 | 解释语义演化或词源 | CC BY-SA 3.0，使用与改作需满足署名及相同方式共享要求 |
| 教材 | 课程顺序、场景覆盖清单、难度感、教学法启发 | 批量复制词表、例句、练习、译文或课次数据 | 默认受版权保护；没有书面许可就只做人类参考，不进入可再分发数据 |
| GitHub 仓库 | 获取有明确 license、可追溯上游、可复现的数据与工具 | “公开可见所以能用”；从无许可证仓库复制内容 | 必须同时检查仓库 license、数据自身 license、上游来源、提交历史与再分发条件 |
| 商业/在线词典 | 人工核对疑难义项、语感、词源线索 | 爬取整库、复制定义或例句 | 除非签订数据授权，否则只作为编辑查证，不能把其表达批量写入产品 |
| AI | 草拟中文表达、生成待审例句、发现冲突、写校验脚本 | 成为真实性来源；自证自己生成的词源 | 产物一律是 candidate；事实字段必须落到外部证据或人工原创责任人 |

可核对的官方/项目资料：

- [jmdict-simplified 项目说明与来源许可](https://github.com/scriptin/jmdict-simplified/blob/master/README.md)
- [SudachiDict README 与 Apache-2.0 说明](https://github.com/WorksApplications/SudachiDict/blob/develop/README.md)
- [Tatoeba 使用条款与署名要求](https://en.www.en.wiki.tatoeba.org/articles/show/terms-of-use-v1)
- [Tatoeba 内容规范](https://en.wiki.tatoeba.org/articles/show/guidelines)
- [KanjiVG 与 CC BY-SA 3.0 许可](https://github.com/KanjiVG/kanjivg)
- [OJAD 功能说明](https://www.gavo.t.u-tokyo.ac.jp/ojad/pages/usage)

重要：这份文档不是法律意见。正式商业发布前，应让熟悉数据许可的人复核 ATTRIBUTION、NOTICE、ShareAlike 范围和 App 内/商店页的归属方式。

### 4.2 推荐的来源组合

普通词典层建议采用：

1. **JMdict 作为日文词条身份主干**：建立稳定 join，不自行凭感觉决定表记/读音/词性。
2. **Sudachi/UniDic 作为机械校验工具**：检查例句是否包含目标词、活用后原形、读音与罗马音，不把它当内容文案来源。
3. **中文释义由言自己编写并承担编辑责任**：参考 JMdict 的 sense 边界，写成适合中文用户的短义项；不能把英文 gloss 机械翻译后称为 verified。
4. **例句优先自写，语料只做候选与自然度证据**：自写能控制版权、难度和旅行场景；Tatoeba 句子若直接采用，必须带来源 ID 与署名。
5. **疑难义项进入人工队列**：多义、惯用、语用限制、敬语、古语、歧义读音，不要自动发布。

这条路线的要点是：中文不是“找一个开放中文词典就结束”。高质量中文释义本来就是言的编辑资产。外部词典负责约束它不能胡写，言负责把它写得适合用户。

### 4.3 词源真实性的止损规则

词源字段分四种状态：

```ts
type EvidenceState =
  | 'verified'     // 有明确权威来源支持
  | 'corroborated' // 两个独立可靠来源一致
  | 'disputed'     // 来源之间有冲突
  | 'editorial';   // 明确只是言的记忆联想，不声称是历史事实
```

展示规则：

- `verified`/`corroborated`：可以写“来自……/由……演变”。
- `disputed`：只在真的有学习价值时写“有两种说法”，否则不展示。
- 找不到可靠来源：留空，不写“据说”。
- `editorial`：必须写成“可以这样记/把它想成……”，不能写成历史事实。
- 单一权威词典足以支持普通字词事实，不需要为了“凑两个来源”重复劳动；真正有争议或很吸睛的故事才要求双源。
- 不做“词源覆盖率”KPI。做“展示出来的事实错误为 0”的质量目标。

`loanSource` 应继续坚持“它是一条边，不是一句散文”：

```json
{
  "lang": "eng",
  "lemma": "apartment",
  "node": "eng:apartment",
  "evidence": ["src:jmdict:ENTRY_ID"],
  "state": "verified"
}
```

### 4.4 字段级 provenance 建议

不要只给整个词条一个 `source: "JMdict"`。不同字段可能来自不同地方：

```json
{
  "id": "ja:注文:ちゅうもん",
  "word": "注文",
  "reading": "ちゅうもん",
  "meaning_zh": "点单；订购",
  "provenance": {
    "identity": ["jmdict:1234560@2026-07-20"],
    "meaning_zh": ["editor:ysy@2026-08-20"],
    "example": ["editor:ysy@2026-08-20"],
    "loanSource": []
  },
  "review": {
    "meaning_zh": "approved",
    "example": "approved",
    "editorial": "not_applicable"
  }
}
```

来源注册表至少记录：

- `sourceId`；
- 名称与主页；
- 精确版本/发布日期/commit hash；
- 许可名称与本地许可文件位置；
- 需要的署名文案；
- 抽取了哪些字段；
- 获取日期与校验和；
- 能否商用、能否修改、能否再分发；
- 上游是否还有第二层许可。

### 4.5 一条可复现的内容流水线

```text
上游数据（固定版本 + checksum）
  → 规范化（表记、读音、sense、稳定 ID）
  → 与现有 8005 词 join
  → 生成三类清单：自动通过 / 冲突 / 未命中
  → 中文编辑与例句编辑
  → 机械校验（目标词、读音、罗马音、重复、字段类型）
  → 人工抽检/核准
  → 写 publication
  → release gate
  → App 运行时再次做最小 schema 校验
```

自动化只负责把人从 8005 条中解放出来，不负责宣布“真实”。每次自动转换都必须留下：输入版本、脚本版本、异常报告和可重跑命令。

## 5. UI/UX 应该怎么优化

### 5.1 首页：只给一个清楚的下一步

当前首页同时承载品牌口号、今日任务、进度、目标选择、学习方式、多个开始入口和词根联动。每块单看都合理，合在一起会让用户再次做课程设计。

建议层级：

1. 第一屏唯一主按钮：继续今天的任务；
2. 次级状态：今天到期、当前旅程/地点、连续或本周进度；
3. 探索入口：场景、世界、词书；
4. 品牌内容如“今日词根联动”下移，且应按日期轮换或基于用户最近学习变化。

修正原则：

- 数字必须可解释，点击后看到同一批内容；
- “今天该复习”不能混入新内容；
- “来自足迹”只统计 `place_checkin` 来源；
- 未开放目标不必占据第一屏的大面积选择位；保留上架占位可以，但降低视觉权重。

### 5.2 词书：把“学”和“查”视觉分开

建议词书首页形成两个明确区域：

- **继续学习**：只展示已发布可学内容与今日进度；
- **查一个词**：搜索全部 Dictionary 内容。

搜索结果中：

- 不向用户暴露内部 `zh_drafted`；
- 显示“基础释义 / 已核学习内容 / 有言卡”这类用户能理解的成熟度；
- 只有可学词显示“开始学习/评分”；
- 仅可查词显示“基础词条，学习内容整理中”；
- 如果允许收藏，按钮叫“存到我的词”，不要伪装成已经学会/评分；
- 词条来源放在详情底部的“内容说明”，不用在主视觉堆 license 名称。

五个 JLPT 级别全部可点并不等于都应该叫“词书”。N3–N1 在未发布前可放到“词典范围”或标“可查询”，不要让用户点进去再发现整本是起草稿。

### 5.3 词详情：建立稳定的信息顺序

推荐顺序：

1. 词、读音、发音；
2. 一个最核心中文义；
3. 分义项与使用限制；
4. 当前义项对应例句；
5. 汉字锚/易错点；
6. 词场或替换练习；
7. 可靠时才出现词源；
8. 内容来源与修订说明。

不要把词源放在核心义之前。用户首先需要学会和用对，之后才需要“为什么”。词源卡可以很迷人，但不能抢走学习主线。

### 5.4 复习：让用户知道为什么今天看到它

卡面建议显示轻量来源：

- “来自：餐厅场景”；
- “你在京都打卡时保存”；
- “地铁第 2 站学过”；
- “手动加入我的词”。

首次出现使用“学习”交互，到期出现使用“复习”交互。两个动作的按钮、进度和结束反馈不要共用模糊文案。

### 5.5 场景：从句子列表变成任务

场景首页先回答“我现在要解决什么”：

- 点餐：看懂提问并完成下单；
- 酒店：办理入住并处理预订查不到；
- 问路：问方向并确认自己听懂；
- 紧急：说清楚哪里不舒服和需要什么帮助。

每个场景按“先认 → 听辨 → 替换 → 自己说 → 完成”组织。句子数量不是进度，完成一个现实任务才是进度。

### 5.6 世界：地图负责发现，列表负责管理

地图适合制造“世界很大”的感受，不适合精确管理 43 个点。建议提供地图/列表双视图：

- 地图：探索与视觉记忆；
- 列表：按去过、想去、国家、最近添加筛选；
- 精选点和自建点视觉区分；
- “去过”需要用户明确操作，不由内容默认 `status: been` 替用户声明；
- 地点详情的语言应由具体使用场景决定，而不是只看国家；多语言地区允许选择。

### 5.7 手账：先让作品可管理，再追求材质感

建议导航：册列表 → 页缩略图 → 画布。画布底部工具分为：照片、文字、已学词、地点印章、票根/素材。必须有：

- 当前页/总页数；
- 自动保存状态；
- 返回后可找到作品；
- 删除/复制页的确认；
- 导出；
- 空态从“最近学习/最近足迹”生成，而不是硬编码京都。

### 5.8 小本子与分账：两个主入口，允许互相跳转

旅行详情可以显示“本次旅行的账本”，但全局也应有独立账本入口。用带文字的分段切换或卡片入口替代纯 Emoji FAB：

- 行程本；
- 分账本。

共享账本页明确展示：在线/本地、成员、最后同步、退出账本、删除本地副本的区别。涉及钱的数据要把同步失败显式告诉用户，不能只 warn。

### 5.9 趣味性：奖励应该是用户经历的证据

优先做以下奖励，而不是通用金币/连续签到：

- 地铁通关票；
- 地点印章；
- 第一次真正说出口的词条；
- 一条旅行路线形成的语言册；
- 学过内容自动成为手账素材；
- “我在这里学会了这句话”的回忆卡。

这些奖励同时服务三层连接：语言、陌生人、自己，也比普通游戏化更符合言的气质。

## 6. 代码冗余怎么处理：分三类，不要一刀切

### A 类：确认引用后可删除

- 未使用的 `MAP_TYPES`；
- 未使用的 `searchPlace` import；
- 新版手账正式替换后、且迁移与生产引用均确认无依赖的旧渲染链；
- 已由自动生成器取代的手写统计注释。

删除前必须用 `rg` 查引用并运行测试；这里只是候选清单，不是授权立即删除。

### B 类：有功能但应合并为单一来源

- `WORD_CARDS_BUILTIN` 与内容包中的 8 张卡：fallback 有价值，但不应手写两份。建议由 release/build 脚本从同一内容源生成 bundled fallback。
- `scripts/validate-content.js` 与现有审计脚本：合并成一套 schema/规则，不保留互相矛盾的 validator。
- 多份 Markdown 中的词数/测试数/功能状态：改为机器报告。
- 多处对“起草/正式”的判断：全部归入 `src/content/publication.ts`。

### C 类：看起来暂时没用，但为未来迁移服务

- journal v1/v2 migration；
- 数据库 schema；
- 稳定词 ID 与 key alias；
- staging 证据和报告；
- moments/cities/assets 模型。

建议给 legacy 目录加一个短说明：


## 11. 最终把关标准

这轮整理完成，不以“文件变短了多少”或“词源补了多少条”判断成功，而以以下问题是否能明确回答判断：

- 用户看到的这个词，为什么可以查？
- 它为什么可以进入学习？
- 它什么时候、从哪里进入了复习？
- 词源是事实、争议，还是记忆联想？
- 每个事实从哪里来，是否允许商业发布与再分发？
- 远端坏内容能否伤到已安装 App？
- 用户的手账与账目能否在重启、登录和失败重试后保住？
- CC 改一个词汇页面时，是否不再需要理解 6000 行 `App.js`？
- 言的趣味是否来自用户真实经历留下的痕迹，而不只是装饰和口号？

言不需要成为“词源最全的日语 App”。它需要先成为一个用户知道下一步做什么、敢相信内容、并能把学到的东西带进真实世界和个人记忆里的产品。
