## 已拍板

### D1 · 分层的轴是「敏感 vs 一般」，不是「照片 vs 进度」

PIPL 第 28 条列举的是**行踪轨迹**，不是"图像"。
风景照不因为是图像就敏感；**照片 + 精确位置 + 时间的组合是轨迹**，GPS EXIF 本身也是。

门槛完全不同：

- 一般个人信息，当年累计不满 **10 万人** → 免予安全评估 / 标准合同 / 认证
- **敏感个人信息没有完全豁免** —— 不满 1 万人也要标准合同或认证

**已查到言的实际情况**（比先前判断严重）：

```
schema.sql:108,141          lat / lng（多张表）
schema.sql:177-178          exif_lat / exif_lng
schema.sql:201-202          travel_checkins 上有 (user_id, lat, lng) 索引
schema.journal.sql:82-83    手账 lat/lng
schema.moments.sql:17       moments lat/lng
features/world/exifImport.js  主动读照片 GPS
```

**推论：只把照片挪到境内 OSS 是白挪的** —— 表里还留着坐标。

### D2 · 豁免的是申报机制，不是保护义务

哪怕落进 10 万人豁免，以下仍然要做（且都是低成本的前端/文档工作）：

- 跨境**单独同意**（不能混在隐私政策的一揽子同意里）
- 告知境外接收方名称、联系方式、处理目的与方式、信息种类
- 个人信息保护影响评估（PIA）并留存三年

### D3 · 不做「为了备案而代理」的网关

境内 ECS 代理 Supabase **不消除数据出境**，只增加延迟、故障点和运维面。
让阿里云资源承担**本来就该在境内做的真实功能**（内容包、媒体、STS 凭证、版本检查）。

### D4 · 现在做抽象层，不做迁移；不砍功能

**理由**：真正贵的不是搬数据（零用户，没有数据），是决定**数据边界**和**账号归属**。
想清楚之后换后端是机械劳动。

- 先做 `ContentAdapter` / `MediaAdapter` / `DataAdapter` / `AuthAdapter`
- `home_region` **注册时确定，跟账号走** —— **不要用当前 IP 判断**
  （用户出国、用 VPN 时 IP 会变，数据会漂）
- 云同步、照片、手账**功能一个不砍**

### D5 · 顺序

```
1. 修完同步链          ← 已完成
2. 内容包迁境内 CDN     ← 与合规无关的纯体验项,技术风险最低
3. 字段级盘点          ← 不知道哪些字段敏感,就没法决定迁什么
4. 抽象层 + home_region
5. 按盘点结果决定迁什么
6. 隐私政策 + 单独同意 + PIA
7. 备案（填报此时是真实的）
8. 大陆区上架
```

## D6 · 备案就直接提交，不要预先去问管局

**驳回不留案底，改了重交即可** —— 这和"备案通过后被注销"是两个量级的事。
所以"日语学习算不算教育类"这类问题，**提交本身就是最便宜的实验**，
比问出一个可能更保守的口头答复强。

- **不要主动去问管局**（执法方，主动提示风险点没有好处）
- 要问就问**阿里云备案专员** —— 你的材料本来就要过他们初审才送管局，
  问他们不叫自爆，是用你已经在付的服务

（工信部 APP 备案通知里教育类需提交主管部门审核同意文件这一条仍然存在，
但是否被归入教育类，交了就知道。）

### D7 · 方案 E：用 CloudKit 代替自建同步（待定，可能是最优解）

**核心事实**：iCloud 在中国大陆由**云上贵州（GCBD）**运营，
是与全球版**完全独立分离**的合规架构 —— 独立运营主体、独立司法管辖、
独立数据流转规则，**大陆 Apple ID 的照片/文件等数据存储在中国境内**。

**推论：用 CloudKit，大陆用户的数据自动落在境内。**
不是"我们去做区域分离"，是 **Apple 已经做完了，而且做到了运营主体层面。**

```
词库内容包  →  阿里云 OSS + CDN     ← 备案填这个,是真实业务
用户数据    →  CloudKit（大陆自动境内）
账号        →  Apple ID（home_region 由 Apple 维护）
海外        →  同一套代码,CloudKit 国际版
```

**同时消掉的东西**：数据出境问题、自建 Auth、同步链运维，
以及 2026-08-30 修的那三处数据丢失 bug —— 它们的复杂度全部来自自建同步链。

**代价**：

1. 需要一次 EAS 构建（CloudKit 在 Expo 里要原生模块 / config plugin）
2. **锁定 Apple 生态** —— 没有 Android、没有 Web
3. 跨用户功能（组队/排行）受限 —— 可单独留轻量后端，
   **只存脱敏分数**（昵称、天数、词数），不敏感、不出境
4. 用户没开 iCloud 就没同步 —— 需 fail closed 退回本地

**唯一可能推翻它的问题：将来要不要做 Android？**

- 不做 → CloudKit 几乎没有缺点
- 要做 → 得再建一套，那不如现在就把 `DataAdapter` 抽好，两边都能接

**这一个问题决定一切，其余都是细节。在回答它之前不要动手。**

## 参考：别人是怎么做的（用来校准，不是照抄）

### 微信 / WeChat —— 一个 App，按注册地分数据平面

**同一个 App，用户到任何国家都不用重新下载**，WeChat 用户与微信用户**可以直接聊天**。
但**注册地决定落在哪个服务实体**（+86 → 境内实体；其他 → 国际实体），
两边服务条款与隐私政策分开，数据按注册地存，**社交图谱打通**。

**这就是 `home_region` 模型最成熟的正例。**（早先"两个 App、数据不互通"的说法是错的。）

### 多邻国 Duolingo —— 单独实体 + 单独构建

```
2021-08  中国安卓商店全面下架（"加强内容合规机制"）
2022-06  重新上架，版本号 5.57.1-china
         开发者主体：Beijing Duolingo Technology Co., Ltd.
         课程对中国用户全部免费
```

**注册中国公司实体 + 单独的 china 构建 + 全免费**（大概率为绕开经营性认定），
而且**先被下架过一次才走通**。

**两条推论**：语言学习类**不是禁区**（它上得去）；
但它走到了实体层面 —— **言现在不需要走那么远，只需要保留走过去的可能。**

### 对言的启示

想要"海内外一起组队排行"是可以的，走它们那条路：
**只同步脱敏聚合数据**（昵称/代号、打卡天数、背词数量），
**不同步照片、位置、聊天**。分数不是敏感个人信息，跨区同步一个分数没有合规压力。

**所以 `home_region` 现在就该在数据库设计里留下** —— 将来做全球榜是加一张聚合表；
不留，就是重构。
