## 三、需要决策的三件事

### 决策 1 · 用户照片和手账是否要迁到境内

大陆上架需要 ICP 备案 + APP 备案（2023-09-26 起，纯离线 App 也要）。
主体和域名已有，**只需新增 APP 备案**。

但备案表要填「云服务 IP 地址」，而实际业务在境外。已知的三种做法：

| | 做法 | 问题 |
|---|---|---|
| A | 备案填境内 IP，业务全跑境外 | **填报与实际不符**；管局抽查发现有注销备案的风险，且会牵连同主体的馋了 |
| B | 境内服务器做 API 网关/中转，境外做存储 | 备案表填的是真实业务 IP；**但数据仍然出境，没解决个人信息跨境问题**；且每次同步多一跳 |
| C | **按敏感度分层**：照片/手账迁到阿里云 OSS（境内），学习进度留 Supabase | 真正减少出境数据；复用馋了现成的 OSS；可增量做。**但学习进度绑定账号，严格讲也算个人信息，风险降低而非清零** |

**当前倾向 C，但不确定它是否足够满足《个人信息保护法》的跨境要求。**

**关键有利条件：现在真实用户约等于零，没有存量数据要迁——这是迁移成本最低的时刻。**

### 决策 2 · 内容包分发（与备案无关，但同样卡大陆）

词库内容包（约 8MB）通过 `raw.githubusercontent.com` 分发。
**开发者本人在国内网络下访问该域名约需 6 秒，完整下载要一两分钟。**
App 顶部因此长期显示「当前使用离线内容」的提示条。

**这意味着即使备案解决了，大陆用户的内容更新体验也是坏的。**
迁到境内 CDN / 阿里云 OSS 是独立于备案的必要项。

### 决策 3 · 时机

已知的工程债（都有工单，正在修）：

- 同步链三处会导致用户数据丢失：云端空表会覆盖本地生词口袋；
  补传途中可能静默新建匿名账号并把数据写进去；删账号时照片可能永久成孤儿
- 词卡对齐显示的中文有一批是错的（已修主要一类，仍有残留）

**当前判断是「先修完同步链，再动存储架构」** —— 在一条已知会丢数据的链上
再叠一层网关或迁移存储，出问题分不清是哪一层。

## Claude

读完了。先说一句前提：我不是律师，下面是基于公开法规原文的分析，涉及具体填报和合规判断的部分建议找一个做数据合规的律师做最终确认——但至少可以帮你把问题问对。

### 一个前置纠正：你的分层维度选错了

文档里方案 C 的分层是「照片/手账 vs 学习进度」，理由是“照片更敏感”。但在《促进和规范数据跨境流动规定》下，真正决定你要不要走合规手续的分层维度是**「敏感个人信息 vs 一般个人信息」**，而这两个维度不重合。

规定第五条第四项：关键信息基础设施运营者以外的数据处理者自当年1月1日起累计向境外提供不满10万人个人信息（不含敏感个人信息）的，免予申报数据出境安全评估、订立个人信息出境标准合同、通过个人信息保护认证。

注意括号——**这个 10 万人豁免只对一般个人信息生效**。敏感个人信息没有任何数量下限：累计向境外提供不满1万人敏感个人信息的，应当订立个人信息出境标准合同或者通过个人信息保护认证；超过 1 万人则要做安全评估。也就是说，哪怕你只有 1 个用户，只要有敏感个人信息出境，就要走标准合同备案。

那么问题变成：**你的哪些数据是敏感个人信息？**

PIPL 第 28 条列举的敏感个人信息里，和你直接相关的是**行踪轨迹**。世界打卡的经纬度、手账的地点坐标、GPS 足迹（你路线图里 Pro 层的功能）——这些是明确列举的敏感个人信息。照片本身不必然敏感（除非用于人脸识别），但**「照片 + 位置 + 时间」的组合就是行踪轨迹**。

所以结论是：方案 C 的方向对，但**理由比你写的更强、要求也比你想的更严**。

- 对：把带位置的打卡/手账数据迁到境内，是有可能把「必须做标准合同备案」这个义务直接消掉的——因为剩下的学习进度、生词口袋是一般个人信息，人数远不到 10 万，落进第五条第四项的豁免。这不是“风险降低而非清零”，在出境手续这一层是有可能真的清零的。
- 严：**只迁存储桶没用**。如果照片挪到了 OSS，但 Supabase 的 checkin 表里还留着 `lat/lng/timestamp`，行踪轨迹照样出境，等于白迁。EXIF 也要处理——很多手机照片自带 GPS 元数据，上传时不剥掉，“照片”本身就是行踪轨迹。这一条文档里完全没提到，是方案 C 最容易做漏的地方。

另外一件必须说清的事：**豁免的是那三条途径，不是告知同意义务**。PIPL 第 39 条要求向境外提供个人信息时告知境外接收方名称、联系方式、处理目的方式、个人信息种类，并取得**单独同意**（不是包含在隐私政策里的一揽子同意）。第 55 条要求事前做个人信息保护影响评估（PIA）并留存三年。这两条不因为你人数少就免除。所以哪怕学习进度继续留 Supabase，你的隐私政策和首次启动的同意流程也得改——这是纯前端工作，成本很低，但漏了是实打实的违规点。

### 关于备案 IP 填报（你的问题 3）

你对方案 A 的判断是对的，而且我想把它说得更重一点：根据《非经营性互联网信息服务备案管理办法》，网站/App 是否需要备案取决于服务器所在地域；若使用中国内地服务器，必须在服务器所属接入商平台完成备案。备案是通过接入服务商提交的，你填的 IP 是“我在这家接入商这里有真实业务”的声明。如果那台 ECS 上跑的东西和 App 毫无关系，这就是虚假备案信息。管局抽查、或者阿里云自己的年度核验发现，注销备案是常规处理，而**注销是针对主体的，会牵连馋了**——这一点你已经意识到了，我只是确认它不是理论风险。

但这里有个好消息：**做完方案 C，方案 A 的问题自动消失了**。词库内容包走境内 CDN、打卡照片走 OSS、再加一个境内的轻量 API 端点，那台阿里云资源上就有真实业务了，填报和实际一致，不需要在材料里“说明”什么——因为没有需要说明的不一致。

所以问题 3 的答案不是“这样填合不合规”，而是**顺序问题**：先让填报变成真的，再去填。

一个补充建议：**给言单独备一个域名**，不要和馋了共用 `chanleapp.cn`。同主体新增网站备案比新主体备案简单得多，但两个产品共用一个域名，任何一边出问题另一边跟着受影响，这个耦合没必要。

### 个人主体的额外限制（你的问题 2）

三点：

1. **非经营性备案个人可以做**（你已经做成一次了），但**经营性 ICP 许可个人主体申请不了**。这对你现在没影响——Apple IAP 的收款方是 Apple，一般不被认定为需要 ICP 许可的经营性互联网信息服务。但如果将来做自建支付、或者做社区/UGC 功能（你路线图里有“用户上传助记”），这两个方向个人主体都会撞墙，社区功能还可能触发额外的内容管理资质要求。这不影响现在上架，但值得在做那些功能之前先想清楚要不要转公司主体。
2. **阿里云的服务码授权限制**：服务器购买账号与备案账号不同时，需由服务器所在的企业认证账号将备案服务码授权给备案账号；个人认证账号无法授权服务码，需先完成企业认证。你如果打算用馋了那台 ECS 给言备案，确认一下是不是同一个阿里云账号——不是的话个人认证账号授权不了，得单独买资源。
3. **App Store 中国区会核验备案号**，Apple 那边是硬性拦截，不是“填了更好”。

### 第四种做法（你的问题 4）

有一个你没列出来的选项，可能比 B 和 C 都更适合你现在这个“用户约等于零”的时刻：

**把 Supabase 自建到阿里云，大陆版走境内实例，海外版继续走 Supabase 云。**

Supabase 是开源的，可以自托管。这个做法的好处是**客户端代码几乎不用改**——同一套 supabase-js 调用，只是换 endpoint 和 key，按 App Store 区域或用户选择路由。相比方案 C（照片走 OSS、进度走 Supabase）需要在客户端维护两套存储 SDK 和两套上传逻辑，自托管的改动面小得多，而且数据分类边界清晰：大陆用户的所有数据都不出境，出境手续问题从根上没有了。

代价是你要自己运维一套 Postgres + Storage + Auth（自托管 Supabase 的运维量不小，尤其 Auth 和 Realtime）。但你已经在阿里云跑着馋了，基础设施熟悉度是有的。

我不确定这个方案对你一定更好——取决于你愿意承担多少运维。但它值得在决策前认真评估一次，因为**在零存量数据的时刻，架构选择的成本差异只体现在开发工作量上，之后就会开始体现在迁移风险上**。

### 顺序建议（你的问题 5）

你现在的判断——**先修同步链，再动存储架构**——是对的，我完全同意，理由你自己已经写出来了：在一条已知会丢数据的链上叠新层，出了问题分不清是哪一层。这个判断值得坚持，不要因为“想早点上架”而跳过。

完整顺序我会这样排：

1. **修同步链**（三处丢数据问题）——阻塞项，不修完不动别的
2. **迁内容包到境内 CDN/OSS**——这一步和备案、和个人信息都无关，纯粹是“大陆用户体验能不能用”的问题，而且技术风险最低，可以最先做完。6 秒首字节 + 一两分钟下载，这个体验下就算备案过了上架了，留存也是零。
3. **决定后端架构**（C 还是自托管），迁移带位置的数据，剥 EXIF，改隐私政策 + 单独同意流程，做 PIA 并留档
4. **备案**——此时填报是真实的
5. **上架**

第 4 步的等待期在 1～20 个工作日不等，且备案审核只审查材料，不会下载 App，可以一边开发一边申请——所以备案材料的准备（包名、证书 MD5、截图等）可以和第 3 步并行，不用串行等。

---

一句话总结：**你文档里最有价值的一句话是“现在真实用户约等于零，没有存量数据要迁”。这句话的含义比你写的更大——它意味着你现在可以自由选架构，而这个自由窗口会随着第一批真实用户的到来永久关闭。** 所以不要为了早两个月上架而选一个将来要迁的方案。

## Grok

**以下为基于现行公开法规与实务的外部意见（截至2026年8月），仅供参考，不构成法律意见。个人开发者场景下建议最终与当地通信管理局或专业律师确认。**

### 1. 方案C（按敏感度分层）在《个人信息保护法》下够不够？

**不够彻底清零风险，但在当前体量下是合理且风险可控的务实选择。**

- 用户照片、手账属于**敏感个人信息**（生物识别/图像类，PIPL第28条）。学习进度、生词口袋、账号体系属于普通个人信息（绑定账号后可识别个人）。
- 《促进和规范数据跨境流动规定》（2024年3月起施行，后续配套持续）对非关键信息基础设施运营者的出境路径是：
  - 当年累计向境外提供**不满10万人个人信息（不含敏感个人信息）**：免予安全评估、标准合同、认证。
  - 敏感个人信息：**没有“不满1万人”的完全豁免**；达到1万人敏感个人信息需安全评估，不满1万人敏感个人信息需标准合同或认证。
  - 另有合同履行必要性等有限豁免，但学习App的云端同步通常难以直接套用。
- 方案C把敏感图像迁到境内阿里云OSS，只让学习进度等普通个人信息留在Supabase：
  - 真正减少了高风险数据出境。
  - 在真实用户≈0、未来用户规模远低于阈值的阶段，几乎不会触发评估或合同义务。
  - 但仍构成“向境外提供个人信息”，需履行告知 + **单独同意**（PIPL第39条），并在隐私政策中明确境外接收方、目的、种类、权利行使方式。
- 结论：风险从“敏感数据出境”降到“小规模普通个人信息出境”，在当前阶段足够实用；若未来用户快速增长或监管抽查加严，仍建议最终把账号体系与进度也迁境内或改为本地优先+可选云同步。

### 2. 个人主体（非企业）有没有额外限制？

**可以，但审核更严，且有品类与经营性限制。**

- 工信部APP备案通知明确个人可办非经营性备案（身份证+手机号即可）。
- 实务中：个人主体审核标准高于企业；涉及教育、内容分发、会员/付费等可能被要求补充说明或被拒；部分省份对个人备案数量、内容有额外要求。
- 你已有同主体的“馋了”备案（浙ICP备2026053105号），新增APP备案复用主体通常可行，但需注意：
  - 同一主体下APP名称唯一性。
  - 若未来有内购、广告变现，可能被认定为经营性，个人主体受限，建议提前规划企业主体。
- 无明确禁止个人做学习类APP的规定，但通过率与后续抽查风险高于企业。

### 3. APP备案时“云服务IP地址”填阿里云ECS，部分业务在Supabase，是否合规？

**存在填报与实际不完全一致的风险，建议谨慎处理并如实说明。**

- APP备案要求如实填报网络接入信息（云服务IP等），由接入商（阿里云等）代提交，管局审核。
- 实务常见做法是：填写境内ECS/OSS作为主要接入点，用于满足备案系统的IP验证。
- 但备案登记表要求真实性。若实际核心业务（尤其账号、进度）长期跑在境外，抽查时可能被认定为“备案信息与实际不符”，存在注销风险，并可能牵连同主体其他备案。
- 建议：
  - 至少把内容包、照片/手账、以及能迁的同步接口放到境内（方案C方向）。
  - 在备案材料或补充说明中如实描述架构（境内接入+部分境外存储），避免完全隐瞒。
  - 备案通过后定期检查公示信息与实际一致。

方案A（完全境外却填境内IP）风险最高；方案B（境内网关中转）可解决IP真实性但未解决数据出境；方案C在真实性与数据合规之间最平衡。

### 4. 有没有比A/B/C更合适的第四种做法？

**推荐“C+”：敏感数据+核心同步接口全部境内化，内容包迁境内CDN/OSS，账号可保留轻量境外或改为境内Auth。**

更优组合：
- 照片、手账、内容包（8MB词库）→ 阿里云OSS + 国内CDN（解决体验与敏感数据）。
- 学习进度/生词口袋 → 尽量迁到境内Postgres/OSS，或做成“本地优先 + 可选云同步（用户明确同意后才出境）”。

你不需要维护两套代码。利用 Expo 的**“公共代码 + 环境变量”**机制。

**第一步：引入“国内版”构建变体**
在 `app.json` 或 `eas.json` 中配置两个构建变体：

- `production` (全球版)：指向 Supabase。
- `production-cn` (国内版)：指向 Supabase + 阿里云 OSS。

**第二步：编写一个“智能存储层” (Smart Storage Wrapper)**
在你的代码中封装一个 `ImageUploader` 类：

```typescript
// utils/ImageUploader.ts

import * as FileSystem from 'expo-file-system';
import { supabase } from './supabase';
import { aliOssClient } from './aliOss'; // 引入阿里云 SDK
import { getRegion } from './networkUtils'; // 简单的 IP 测速或 GeoIP 库

export async function uploadPhoto(uri: string, userId: string) {
  // 1. 判断用户位置 (可以缓存这个结果，不要每次上传都判断)
  const region = await getRegion(); 
  const isChinaMainland = region === 'CN'; 

  if (isChinaMainland) {
    // 🇨🇳 国内逻辑：上传到阿里云 OSS
    // 注意：为了安全，不要在前端暴露阿里云 AccessKey Secret。
    // 建议：利用 Supabase 的 Database Webhook 或 Edge Function 生成阿里云的临时 STS Token。
    const path = `photos/${userId}/${Date.now()}.jpg`;
    await aliOssClient.put(path, uri);
    return `https://your-cn-bucket.aliyuncs.com/${path}`;
  } else {
    // 🌍 海外逻辑：上传到 Supabase
    const { data, error } = await supabase.storage
      .from('checkin-photos')
      .upload(`${userId}/${Date.now()}.jpg`, uri);
    
    if (error) throw error;
    return data.path;
  }
}
```

**第三步：关于阿里云密钥的安全问题**
你可能会担心：“把阿里云的 Key 写在前端代码里，会被黑客盗用刷流量吗？”

- **解决方案：** 利用你现有的 Supabase。
  - 在 Supabase 上写一个简单的 Edge Function（或者利用你备案用的那个阿里云 ECS 小服务器）。
  - App 启动时，请求这个接口：“我要上传照片，给我一个阿里云的临时上传凭证（STS Token）”。
  - 服务器下发一个有效期只有 15 分钟的 Token。
  - App 拿着这个临时 Token 直传阿里云 OSS。
  - **结果：** 既安全，又实现了分流。

#### 3. 回答你之前的疑问（基于新视角）

- **关于备案填 IP：**
  - 现在你可以理直气壮地填阿里云 ECS 的 IP。因为你的国内版 App 确实会频繁访问阿里云（上传照片、下载词库）。这不再是“挂羊头卖狗肉”，而是真实的“混合云架构”。
- **关于个人主体：**
  - 个人主体最怕“数据出境”。现在你把最敏感的照片留在了国内，剩下的文本数据（学习进度）出境，监管容忍度会高很多。
- **关于内容包（词库）：**
  - 同样做分流。国内版 App 从阿里云 OSS 下载词库，海外版从 GitHub 下载。这能彻底解决国内用户“转圈圈”的问题。

### 总结建议

**不要为了进大陆市场而放弃你的海外架构，也不要为了海外架构而硬闯大陆合规红线。**

**最佳路径：**

这样，你既拥有了一个合规的“中国版 YanApp”，又保留了原本清爽的“全球版 YanApp”，虽然多写了几十行代码，但这是性价比最高的方案。

**回答：方案 C 是目前技术成本与合规风险平衡下的最优解，但需注意“账号体系”的处理。**

- **为什么方案 C 可行：**
  - **规避了“数据出境”申报门槛：** 根据《个人信息保护法》，向境外提供个人信息通常需要极高的合规成本（安全评估/认证）。方案 C 将最敏感、体积最大的**图像数据（照片/手账）**留在了境内（阿里云 OSS），这符合监管对“核心数据本地化”的要求。

规划共享、组队这类涉及多用户交互的功能时，数据合规是核心，主要挑战在于数据存储地和用户间数据流转的规则。

    1.  **获取明确同意**：在隐私政策中清晰告知用户数据共享的方式和范围。

关于国内外用户的数据路由，关键在于“数据属地化”原则。国内用户的数据，**必须存储在国内的服务器上**。因此，“部分业务在境外”的方案只适用于海外用户。

*   **理想架构**：构建两套独立的后端环境。
    *   **国内环境**：部署在阿里云等境内服务商，存储和处理所有国内用户数据。
    *   **海外环境**：可继续使用Supabase等服务，服务海外用户。
*   **用户归属判定**：App应根据用户的**网络环境（IP地址）**或**主动选择的地区**，自动将用户路由到对应的后端环境。
*   **“出国旅游”场景**：这不会改变用户的“数据属地”。一位中国用户出国旅游，其数据依然存储在国内服务器，App通过互联网正常访问即可，与物理位置无关。反之，外国用户来华，其数据仍应路由至其归属的海外服务器。

## 二、六家回答里，最重要的事实纠偏

### 1. 一般个人信息 < 10 万人：不是“一出境就必须标准合同”

《促进和规范数据跨境流动规定》第五条第四项明确：非关键信息基础设施运营者，自当年 1 月 1 日起累计向境外提供**不满 10 万人个人信息（不含敏感个人信息）**，免予：

1. 数据出境安全评估；
2. 个人信息出境标准合同；
3. 个人信息保护认证。

因此，如果 Supabase 里只剩：账号标识、学习进度、生词口袋等**一般个人信息**，而且人数远低于 10 万，不能说“只要留 Supabase 就必须标准合同”。

Gemini 第一轮、千问等对此说得过重。

### 2. 敏感个人信息的门槛完全不同

对于非关键信息基础设施运营者：

- 不满 1 万人的敏感个人信息出境：原则上走**标准合同或个人信息保护认证**；
- 1 万人以上敏感个人信息出境：进入**数据出境安全评估**。

所以真正决定方案 C 是否干净的，不是“照片 vs 学习进度”，而是**Supabase 最终还剩不剩敏感个人信息字段**。

### 3. “照片 = 敏感个人信息”不准确

《个人信息保护法》第 28 条列举的是：生物识别、宗教信仰、特定身份、医疗健康、金融账户、**行踪轨迹**等，以及不满 14 周岁未成年人的个人信息。

因此：

- 一张普通风景照，并不会仅因为“是图像”就自动成为敏感个人信息；
- 如果照片被拿来做人脸识别/身份识别，可能落入生物识别信息；
- 精确 GPS、连续位置历史、可形成个人活动轨迹的数据，属于更明确的敏感个人信息风险；
- 照片携带 GPS EXIF，或者 check-in 表保留精确 `lat/lng`、时间并能持续拼出轨迹，应按敏感数据边界来设计。

中国并不存在一个适用于所有普通 App、所有用户的“个人信息一律本地化”规则。

《个保法》第 40 条的境内存储义务主要针对关键信息基础设施运营者，以及达到国家网信部门规定数量的个人信息处理者；同时 2024 年《促进和规范数据跨境流动规定》又给小规模一般个人信息出境提供了明确豁免路径。

## 三、你特别问到的 IAP：个人开发者确实可以做

## 五、备案 IP：不要做“为了备案而代理”的网关

这里我和几家模型有一个重要分歧。

**境内 ECS 做一个真实业务节点是好事；但仅仅为了让备案看起来像境内业务，把所有 Supabase 请求再代理一遍，没有必要。**

原因有三点：

1. 代理并不会消除数据出境：ECS → Supabase 仍然是出境；
2. 代理增加延迟、故障点、日志和运维面；
3. “隐藏 Supabase 地址”不是合规目标。

真正合理的是让阿里云资源承担**本来就值得在境内做的真实功能**：

- `content.yan...`：词库版本/内容包 → OSS + CDN；
- `media.yan...`：大陆侧打卡/手账媒体 → OSS；
- `api-cn.yan...`：STS 临时凭证、内容版本、必要的 CN metadata / 删除任务；
- 如果以后大陆学习数据也境内化，再让 `api-cn` 承担数据 API。

这样备案填写阿里云接入资源不是“空挂”，也不需要为了备案把所有海外流量强行绕一圈。

阿里云自己的 APP 备案文档明确要求填写真实 App 信息，并说明使用阿里云云产品作为 App 后台服务器的原生 App 可以通过阿里云办理备案。**至于混合云架构里具体哪个 IP/资源需要填、是否需要补充说明，应该以阿里云备案订单里实际字段和浙江管局反馈为准，不能靠模型编一个“统一拓扑规则”。**

## 六、我最推荐的架构：不是 C，也不是“全量境内 D”，而是 D2 · Global-first 双区域

### 1. 全局层

```text
Yan App
  │
  ├── ContentAdapter
  │     ├── CN: Aliyun OSS/CDN
  │     └── Global: Global CDN / GitHub/Supabase origin
  │
  ├── MediaAdapter
  │     ├── CN-home: Aliyun OSS
  │     └── Global-home: Supabase Storage
  │
  ├── DataAdapter
  │     ├── CN-home: 现阶段可“本地 + 一般数据 Supabase”，未来可切境内 DB
  │     └── Global-home: Supabase Postgres
  │
  └── AuthAdapter
        ├── 现阶段：Supabase Auth + Apple Sign in
        └── 未来：必要时为 CN-home 增加境内身份映射层
```

核心不是现在就买两套数据库，而是**先把调用层抽象出来**。这样将来换供应商只是换 adapter，不是重写业务层。

### 2. `home_region` 不要用“当前 IP”决定

Gemini/千问提到按 IP 或手机号实时路由，这个思路我不建议。

否则会出现：

> 用户上海注册 → 去日本旅行 → App 判断成 Global → 同一个账号突然写进另一套数据库。

这会制造真正的数据灾难。

建议给账号一个稳定字段，例如：

```text
home_region = CN | GLOBAL
```

它在账号建立时确定，并长期固定。短期旅行**不改变 data shard**。如果未来用户永久迁居，再提供一次显式的“账户区域迁移”流程。

这个字段是你的**工程数据归属**，不是对国籍、民族等身份的判断。

### 3. 用户出国旅游怎么办？

访问地点变化 ≠ 数据必须迁库。

CN-home 用户去东京旅行，照样读写自己的 CN-home 数据；海外用户来上海旅游，也不需要因此把全部历史数据临时搬进阿里云。

真正需要重新判断的是：某项**新数据在哪里收集、包含什么、要不要跨境同步**，而不是看护照或当前位置粗暴换数据库。

## 七、未来海内外能不能一起组队、排行？能，而且不要求所有数据库合并

这是你未来产品架构最值得提前留一条缝的地方。

可以做一个很薄的 **Global Team / Leaderboard Federation Layer**：

### 本地私有数据不跨区

CN-home：
- 照片原图
- 精确位置
- 私人手账
- 全量学习日志

继续留在 CN 数据面。

Global-home 同理留在全球数据面。

### 跨区只交换“组队所需最小事件”

例如：

```json
{
  "public_user_id": "u_xxxx",
  "team_id": "t_xxxx",
  "display_name": "生米",
  "score_delta": 20,
  "streak_days": 6,
  "event_type": "daily_words_completed",
  "occurred_at": "..."
}
```

不要为了排行榜同步：原始照片、GPS、完整学习明细、邮箱、Apple ID 等。

但要注意：**“假名 ID + 分数”只要还能关联回具体用户，仍可能是个人信息，只是去标识化，不是当然的匿名信息。** 因此跨境时仍按一般个人信息规则管理；在你当前体量下有 <10 万人机制豁免，但仍要做必要性、告知/单独同意、PIA 等。

这恰好说明：**保留全球架构并不等于让所有原始数据全球复制。** 以后完全可以让中国和海外用户同队、同榜，而只有最小的“比赛事件”跨区。

## 八、以后从个人转公司：通常不是“把数据库搬一遍”

这也是前面几家回答里容易说混的地方。

### Apple 侧

Apple 官方明确支持申请把 **Individual membership 更新为 Organization membership**。通常要求你是组织的创始人/共同创始人，并提供 D-U-N-S 等组织资料。

因此未来并不一定要：

> 新建一个公司 Apple 账号 → 整个 App 重新上架。

Apple 也支持 App Transfer；如果确实用了不同账户，满足条件时可以转移 App，并保留 Bundle ID、评论和评分等。

### 数据库侧

“主体变公司”本身不要求数据库物理搬家。

真正可能变化的是：

- Supabase / 阿里云合同主体；
- 隐私政策中的个人信息处理者名称；
- 数据处理协议、支付/税务信息；
- ICP/APP 备案主体；
- Apple Developer seller / organization 信息。

如果法律上的个人信息处理者从“你个人”变成“某公司”，需要按具体转换方式处理告知、合同和数据资产承接问题；但这和“把每条 Postgres 数据导出再导入”是两回事。

### 真正的长期成本

注册或转换那一下的行政费用往往不是大头。更持续的成本是：

- 记账报税；
- 银行账户；
- 年报；
- 合同与财税；
- 如未来申请增值电信业务许可，对公司、人员、注册资本等还有额外条件。

所以不值得为了一个**尚未上线的远期社交功能**现在就背上完整组织运营成本。

## 十、我建议你现在真正做的顺序

### P0 · 先把已有数据链修稳定

1. 云端空表不允许覆盖有效本地学习数据；
2. 补传过程中不允许静默漂移到新匿名 UID；
3. 删除账号时 DB、Storage、引用关系必须能收敛，不留下永久孤儿；
4. 给关键同步操作加可追踪日志 / migration version。

**这仍然是阻塞项。**

### P1 · 与同步链低耦合、可以先做的大陆体验改造

1. 8 MB 词库内容包迁阿里云 OSS/CDN；
2. 做 `ContentAdapter`，国内/海外源可配置切换；
3. 不要再以 `raw.githubusercontent.com` 作为大陆主更新源。

### P2 · 做字段级数据盘点，而不是“按表猜敏感度”

至少列：

| 字段/数据 | 是否可识别 | 是否可能敏感 | 当前位置 | CN 目标位置 | 是否出境 |
|---|---|---|---|---|---|
| auth uid | 是 | 一般 | Supabase | 暂留 | 是 |
| Apple 登录标识 | 是 | 一般 | Supabase | 暂留 | 是 |
| 单词进度 | 是（关联 uid） | 一般 | Supabase | 暂留 | 是 |
| 精确 lat/lng | 是 | **行踪轨迹风险** | 待核 | **境内** | 否 |
| GPS EXIF | 可能 | **行踪轨迹风险** | 图片内 | 上传前处理/境内 | 否 |
| 打卡原图 | 是/可能 | 视内容与用途 | Supabase | OSS CN | 否 |
| 私人手账图 | 是/可能 | 视内容与用途 | Supabase | OSS CN | 否 |

### P3 · 只把该境内化的部分先境内化

- 照片/手账媒体；
- 精确位置、轨迹字段；
- 与这些敏感字段紧密绑定的 metadata；
- STS/删除/媒体生命周期 API。

如果最终核完发现 Supabase 只剩一般个人信息，那么你当前人数下的出境机制负担比“全量迁国内”轻得多。

### P4 · 合规文本和流程

只要有一般个人信息继续给境外 Supabase：

- 跨境事项单独告知；
- 取得单独同意；
- 做一份 PIA 并留档；
- 记录境外接收方、目的、字段、保存期限、删除方式；
- 后续用户量与敏感字段变化要能监测。

### P5 · 让阿里云成为真实业务资源后，提交 APP 备案

备案材料可以提前准备；真正提交时尽量保证填报架构已经存在，而不是“先写一个未来会做到的 IP”。

### P6 · 大陆区上架

拿到 APP 备案号后，在 App 内显著位置显示，并按 Apple 中国大陆 App Store 要求提交 ICP Filing Number。

# 第四部分 · 多模型结论可靠度速览

| 观点 | 判断 |
|---|---|
| “先修同步链，再迁架构” | **高度一致，正确** |
| “词库立刻迁境内 OSS/CDN” | **高度一致，正确** |
| “小规模一般个人信息出境 <10 万无需三大出境机制” | **法规明确** |
| “只要任何个人信息出境就必须标准合同” | **错误** |

| “照片天然是敏感个人信息” | **错误/过度概括** |
| “精确行踪轨迹属于敏感个人信息” | **法规明确** |
| “个人主体没有数据出境合法路径” | **缺乏依据/错误** |
| “中国用户所有数据必须存国内” | **错误的笼统说法** |
| “个人 Apple 开发者不能 IAP” | **错误** |
| “有 IAP 就必然需要公司主体” | **不能这样直接推导，需按具体业务判断** |
| “个人主体绝对不能任何 UGC/组队” | **过度确定；未来复杂度确实明显上升** |
| “ECS 代理 Supabase 就解决跨境” | **错误** |
| “为了备案把 ECS 做成真实业务节点” | **合理** |
| “按当前 IP 实时决定数据存哪边” | **工程上不推荐** |
| “海内外用户未来可以同队同榜” | **技术上完全可行，建议做最小跨区事件层** |
| “个人转公司一定要迁数据库” | **错误；法律主体/合同变更与物理迁库是两回事** |
