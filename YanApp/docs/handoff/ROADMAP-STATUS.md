# 完整路线图 · 分阶段核对状态

> 对应：`docs/ROADMAP-content-trust-structure-ui.md`
>
> 原则：完整路线图是独立审查与建议，不是一次性施工命令。每项必须经过“代码核对 → 产品决定 → 小工单实现 → 独立复核”。

## 状态含义

| 状态 | 含义 |
|---|---|
| `审查发现` | Codex 根据当前代码/数据提出，尚未由 CC 对调用链复核 |
| `CC 核对中` | 当前 `ACTIVE.md` 指定 CC 只核对这一项 |
| `代码事实确认` | 双方对当前行为与影响路径一致 |
| `待产品决定` | 技术事实已清楚，但产品取舍需要产品负责人确认 |
| `已授权实现` | 已形成边界明确的小工单 |
| `已实现待复核` | 实现者完成，等待另一代理审查 diff |
| `完成` | 实现、测试和独立复核完成 |
| `暂缓` | 有价值但不是当前阶段任务 |

## CC 怎样核对完整路线图

CC 不需要全文审阅并给“同意/不同意”的总评。每次只做一行：

1. `ACTIVE.md` 指定当前项目；
2. 只读路线图对应章节；
3. 用 `rg` 找实际调用路径；
4. 把当前行为、遗漏、过时结论写进 `CC-REPORT.md`；
5. 不编码；
6. Codex 再复核 CC 的报告与代码；
7. 产品负责人决定是否授权实现；
8. 本表更新状态。

## 为什么不一次核对全文

- 路线图包含内容、学习、世界、手账、分账、UI 和长期架构，完整核对会把多个领域装入同一上下文；
- 有些章节是产品判断，不是 CC 能通过代码证明或否定的事实；
- 有些数字会随内容包变化，应由脚本重算，而不是花额度逐字对照；
- 一次核对太大，容易再次出现“看见问题就顺手修、修着修着改变范围”。

严峻不等于同时开工。P0 必须认真处理，但要串行完成；P1–P3 只是后续边界和保护，不是当前积压的五十个紧急 bug。
