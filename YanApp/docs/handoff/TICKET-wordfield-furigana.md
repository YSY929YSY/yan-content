# 工单 · 给 229 条词场补读音行（派生，不写进内容包）

> 先读 `AGENTS.md`（第五节 5-1~5-5、第七节诚实要求）。
> **本轮不碰内容包、不落库、不开内容分支。**

## 本轮决策指标（5-4）

**229 条 Tatoeba 词场里，能正确派生出读音的条数。**

不是"跑通了"，是**对多少条能给出与真实读音一致的假名**。
派生不出来的必须留空 —— **宁可少一行，不能给错读音**。

## 这张工单把主线推迟多久

**不推迟。** 半轮，且不与任何内容包任务冲突。

## 为什么做

真机上有一个肉眼可见的不一致：

```
手工 20 条词场    有读音行（wordField.sentence.roma，存在内容包里）
Tatoeba 229 条    没有读音行
```

落库时的裁决是**不生成假名**，因为写进内容包等于产出无源内容。**那条裁决不变。**

**这一轮改的是运行时派生** —— 和 gloss 同性质：不写进内容包，
每次渲染时算出来。派生数据不是编造内容。

## 要做的

### 1. 运行时派生读音

用项目已有的东西，**不要新引依赖、不要新写假名规则**：

- `src/features/wordbank/furigana.ts` 的 `alignFurigana()` / `canAlign()`
- `assets/example_tokens.json`：每个 token 自带读音
  （形如 `[["全部","ぜんぶ"],"で",["三千","さんせん"]]`）
- `wordFieldAlignment.js` 已经把句子切成 token 了

**注意**：`EXAMPLE_TOKENS` 是按**例句词条 id** 索引的，词场句不在里面。
所以词场句的 token 读音**没有现成索引** —— 先确认这一点，
在报告里写清楚你实际是从哪里拿到读音的。
**如果拿不到，就说拿不到，不要用推测的假名凑数。**

### 2. fail closed（不变量 4）

- 整句派生不出来 → **不渲染读音行**（`App.js:2590` 已经是 `{!!roma && ...}`，天然安全）
- 部分 token 派生不出来 → **整行不渲染**，不要拼一半
- **绝对不许猜读音。** 多音字、人名、外来语拿不准就留空

### 3. 决策指标出数

对 229 条给出：

- 全句可派生：`?` 条
- 部分可派生（按上面规则整行留空）：`?` 条
- 完全不可派生：`?` 条
- **抽 20 条派生结果贴进报告**，日文 + 派生假名 + 现有手工 20 条的格式对照

### 4. 抽查正确性（比覆盖率重要）

派生出来 ≠ 派生对了。

从手工那 20 条里挑 **有 `roma` 的全部 20 条**，用同一套派生逻辑跑一遍，
**与内容包里人工写的 `roma` 逐字比对**。

- 一致率是多少？
- 不一致的逐条列出，判断是派生错了还是人工写法不同（如全角空格、分词位置）

**这 20 条是唯一有标准答案的样本，必须用。**

## 明确不做

- ❌ **不把读音写进内容包**（`content.fallback.json` / `content.v2.json` 都不碰）
- ❌ 不新引任何假名/分词依赖
- ❌ 不改 `wordFieldAlignment.js` 的分词与查词逻辑
- ❌ 不改 `furigana.ts`（只读，见 `AGENTS.md` 只读清单外的判断：
  **如果非改不可，停下来说明理由再动**）
- ❌ 不猜任何读音
- ❌ 不构建、不发 OTA
