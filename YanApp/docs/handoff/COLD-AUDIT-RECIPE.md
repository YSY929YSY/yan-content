# 冷启动审计 · 配方

> 通用版，**言和馋了都能用**，换掉「范围」那一段即可。
> 战绩与规矩见 `AGENTS.md` 5-6。

## 它和「换个 AI 问一遍」的区别

| | 能做什么 |
|---|---|
| 换个 AI（GPT / Gemini） | 只能对你粘贴的内容推理。**强在判断**（语言质量、产品直觉），**弱在核实**——它说「这里可能有问题」，但验不了 |
| 冷启动 subagent | 有全部工具，能 grep、能跑脚本、能自己复算。**强在核实** |

**真正起作用的不是「换了个模型」，是「没看过产生这段代码的那段推理」。**

两次审计找到的东西，主审计侧（同一个模型）全都漏了。
**共享模型不要紧，共享对话才要命。**

## 什么时候派

- 改完「测试输入」与「运行时输入」可能不一致的代码（对齐、渲染、同步）
- 动内容包 / 发布链之前
- 一段时间没审过的子系统（每 5–8 轮一次）
- **上架前**（`DECISIONS.md` 那一节）

## 简报模板（照抄，换掉方括号内容）

```
你在审计 [项目一句话描述]（仓库根 [路径]）。

**任务：对抗性审查 [子系统名]，找出正确性问题。**

## 背景（只给事实，不给结论）

- [关键文件及其职责，3~6 条，纯陈述]
- [最近相关的 commit hash，让它自己 git show]

## 重要约束

- **[大文件名] 有 N 行，不要整份读。** 用 grep -n 定位后 sed -n 'A,Bp' 只读相关段落。
- **只读审计，不要修改任何文件。**
- **不要相信 docs/ 里的说法** —— 那里有大量报告声称某些问题已修复。
  **你的任务是自己验证，不是复述它们。** 引用任何数字必须自己跑一遍确认。
- 不要碰生产凭据，不要连远端。

## 攻击方向（不要局限于此）

1. **纯函数的调用方传了什么？** 追踪入参在真实路径上的实际取值，和测试里传的对比。
2. **哪些断言不可能失败？** 找出即使代码坏掉也不会转红的测试。
3. **数据完整性**：有没有自相矛盾的行？
4. **失败时的行为**：字段缺失、查不到、数组为空时，取最保守的值还是当成「可以」？
   **重点找 fail-open**：`x && guard && !guard.has(y)` 这种 guard 为 null 时整体短路的形状。
5. 任何你觉得可疑的地方。

## 输出

每条包含：具体位置（文件:行号）· 失败场景（什么输入 → 什么错误结果，具体到可复现）
· **你实际跑的验证命令和输出**（不是推测）· 严重性。

**没找到问题也要说。编造问题比漏掉问题更糟。**
最后单独写一节：你做了哪些假设，为什么。
```

## 四条最关键的，写错就白派

1. **不要告诉它已经发现了什么** —— 否则它只会来确认你的结论
2. **明写「不要相信 docs 里的说法」** —— 报告攒到几千行时，
   冷启动 agent 最容易做的事就是复述它们，那等于没审
3. **要求贴实际跑的命令和输出**，不是推测
4. **写明「没找到问题也要说」** —— 否则它会为了显得有用而凑几条无关痛痒的

## 拿到结果之后

**逐条自己复算再采信。** 两次审计我都复算过，数字都对，
但这一步不能省 —— 它也可能错，而且它的错更难发现（它没有上下文能自我纠正）。
