## 追加裁决 · 结构冲突（2026-08-26，三条）

Codex 指出工单自相矛盾：「按现有结构不要新造字段」与「保留 Tatoeba ID」不能同时满足。
**停下来问是对的。** 裁决如下。

### (1) `wordField.source`：加

**「不要新造字段」是工单措辞过头，不是项目约定。**
`AGENTS.md` 只读清单里明写：`contentSchema.ts`（运行时形状闸门，
**新增可选字段不需要改它**）—— 项目本来就预期可选字段扩展。

「来源 ID 只留 staging」不接受：`staging/` 是未跟踪的工作区产物，
那样内容包里的句子就无源可查，而**每条可定位到来源正是言的 moat**。

结构：

```json
"source": { "provider": "Tatoeba", "jp_sentence_id": 123, "zh_sentence_id": 456 }
```

**只给这 167 条加，不回填现有 20 条**（它们是手工精选，provider 不是 Tatoeba，
硬填等于编造来源）。现有 20 条缺来源这件事写进报告作为已知缺口。

### (2) 「未经母语者确认」：不加字段

**不需要新字段。** `AGENTS.md` 不变量 4 是 fail closed —— 缺字段一律取最保守值。
所以 **缺 `nativeChecked` 即视为未确认**，这已经是正确语义。

将来真有母语者确认了，才写 `nativeChecked: true`。这样现有 20 条与新的 167 条
**语义一致，不用回填**，也不会出现「一批有标记一批没有」的分叉。

**工单第 3 步「标注未经母语者确认」因此改为：什么都不写。** 在报告里说明依据。

### (3) `roma`：省略该键，不要生成

现有 20 条 **20/20 都有 `roma`**（假名读音），Tatoeba 候选一条都没有。

渲染端已经 fail-safe（`App.js:2590`：`{!!wordField.sentence.roma && ...}`），
**缺了就不渲染读音行，不会崩。**

- ❌ **不要生成假名读音** —— 那是无源产出
- 已知视觉后果：这 167 条比现有 20 条**少一行读音**。**不阻塞落库**；
  读音以后可用项目已有的 `furigana.ts` 批量派生（派生数据，和 gloss 同性质），
  那是独立的一张工单。

### `members` 映射

现有形状是 `[{ "id": "n5_tomodachi" }]`，shortlist 里是 `member_word_ids` 字符串数组。
按现有形状映射，**不要改成字符串数组**。
