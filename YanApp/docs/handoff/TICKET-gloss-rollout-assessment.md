# 工单 · 例句 gloss 推广前的覆盖率评估（只测量，不改 UI）

> 先读 `AGENTS.md`（第〇节主线、第六节交报告前必做）。
> **本批只测量，一行 UI 都不改。** 这是 ROADMAP「工作包 0：只测量，不改行为」的同一种做法。

## 为什么先测量

样板两句（`店員にカードを見せます。` / `店員にサイズを聞きます。`）已经能显示
三槽位 + 逐块理解。但**能不能推到全部 4400 条例句，取决于两个数，而这两个数还没人量过**：

1. **拼回去一致率** —— `buildWordFieldAlignment` 用的是自己的贪心分词，不是 Sudachi。
   拼回原句不一致就必须退回纯文本（少一个假名可能就是另一个意思）。
2. **gloss 覆盖率** —— 词场那 20 句是 100%，但那是精挑的句子。4400 条例句里
   会出现大量不在词库的词。

**先量，再决定推不推。**

## 要做的

新增 `scripts/gloss-coverage.mjs`（只读，不写任何文件），对**全部有例句的词条**跑一遍：

### 必须给出的数字

| 指标 | 说明 |
|---|---|
| 可用率 | 拼回去 === 原句 的句子数 / 总数 |
| gloss 覆盖率 | 有中文的 token 数 / 总 token 数（**排除标点**） |
| 全覆盖句子数 | 每个 token 都有中文的句子有多少 |
| 分布 | 按覆盖率分桶（100% / 90-99% / 70-89% / <70%）各多少句 |
| 空白成因 | 留空的 token 按类型分组（活用碎片 / 表记差异 / 不在词库），各占多少 |
| 与 Sudachi 分词的差异 | 贪心分词和 `EXAMPLE_TOKENS` 切得不一样的句子有多少 |

### 必须抽样

- **随机 15 句**贴进报告，每句显示：原句 / 逐 token 的 jp→zh / 哪些留空
- **另外挑 5 句覆盖率最低的**贴出来 —— 最差的样子比平均值更能说明该不该推

### 明确不做

- ❌ **不改 UI**、不改 `App.js`、不动 `TOKEN_COLUMN_SAMPLE_SENTENCES`
- ❌ 不改 `wordFieldAlignment.js` 的分词或查词逻辑（**这一轮是测量，不是优化**）
- ❌ 不碰内容包
- ❌ 不构建、不发 OTA
- ❌ 不用 LLM 补任何中文

### 验收

- 脚本只读，跑两次 `git status --short` 干净
- 上面每个数字都在报告里
- `npm test && npm run typecheck && npm run audit`
