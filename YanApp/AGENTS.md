## 一、不变量（任何一轮都不许破，工单不用再抄一遍）

1. **进度键格式不变**：`unitKey('word', …)` 永远是裸的 `词-读音`，不加前缀。
   改了等于所有线上用户的学习进度一夜归零。别名折算在 `srs.normalizeProgress` 读盘时做完。
2. **`kanji_anchor` 是 563 条**。不给任何词加这个 feature —— 它的语义是「汉字跨语言记忆锚」，
   给片假名词加上去就是污染 moat 的定义。首页主 CTA 的池子靠它。
3. **不改评分算法**：`src/features/wordbank/srs.js` 的 Leitner 阶梯与三档评分。
   可以改「什么时候调用它」，不能改「它怎么算」。
4. **fail closed**：任何新增判断，缺字段一律返回最保守的值。
   `publication` 缺失 = 不可学；`meaningTrust` 缺字段 = 机器稿；`writeGuard` 读不到 = 不许写。
   这个项目栽过四次的形状都是把「不知道」当成了「可以」。
5. **不拆 `App.js`**。那是 ROADMAP 工作包 5，是独立的事，不许顺手做。
6. **不许顺手重构**。看到烂代码写进报告，不要改。
7. **用户可见文案里不出现内部状态词**：`candidate` / `draft` / `zh_drafted` / `verified` / 
   `human_reviewed`。要说就说人话。
8. **不许宣称证明不了的事**：「高频」「官方」「必考」「已核验」——
   除非有可定位的来源。理由见 `docs/AUDIT-source-trust-2026-08-22.md`。
9. **`tags.scene` 是 product_taxonomy，不是事实断言**。它不需要来源、不进 claim/evidence 流程。
   别让 source-audit 的标准误伤它。
10. **新增测试必须放在 `__tests__/` 目录下**。有守卫（`src/lib/__tests__/testsAreRun.test.mjs`），
    放错地方会红 —— batch3/4 有两个测试文件因此从没被跑过。

## 二、文件锁

### 🔒 `assets/content.fallback.json` —— 全局互斥

**同一时间只能有一个任务持有。** 多个内容改动排成一个「内容窗口」，串行做完，窗口结束发一次远端包。

改它的时候**必须在同一个 commit 里同时改两份文件**：

```
YanApp/assets/content.fallback.json
yan-content/content.v2.json          ← 漏过一次，见下
```

提交前 `shasum -a 256` 确认两份逐字节相同（审计有这条硬要求）。

**为什么**：`scripts/push-content.sh` 取的是 `git show develop/v2:yan-content/content.v2.json`——
**已提交的那份**。2026-08-22 只改了 fallback、没提交 content.v2.json，结果两份文件在磁盘上
逐字节相同、审计 Blocker=0、测试全绿，**而权威副本停在旧版本，照那样发布线上拿到的是旧包**。

### ⚠️ `App.js` —— 代码级共享文件

两条线都会碰它，但位置通常不重叠。**不要让两个 subagent 同时写它**，按 commit 顺序串行落地。

### 📖 只读，不许改

`srs.js`（评分）· `units.js`（五来源归一）· `publication.ts`（发布契约）· 
`contentSchema.ts`（运行时形状闸门，**新增可选字段不需要改它**）· `sourceAudit.ts` · 
`keyAliases.js` / `wordIds.manifest.txt`（进度键保护）· `staging/**`（除工单明确指定的产出）

---

### 🌿 分支规矩：只有内容窗口开分支

**默认在 `develop/v2` 上直接提交。** 脚本、文档、UI、测量 —— 都不开分支。

**唯一例外：改 `assets/content.fallback.json` 的任务。**
开 `content/<日期>-<主题>` 分支，窗口做完、`bash tools/check-content-release.sh` Blocker=0
之后再合回 `develop/v2`。

理由**不是**防冲突（工单是串行的，本来就不冲突），是**可回滚**：
内容包是全局互斥文件，且发布即线上。

### ⚠️ `main` 不是开发分支，是发布通道

`scripts/push-content.sh` 把 `develop/v2` 的 `content.v2.json` 推到 `origin/main` ——
**App 从 `origin/main` 读内容**。

所以在这个仓库里，**merge 到 main = 给线上用户发内容包**，不是普通合并。
任何"跑完门禁自动合进 main"的流水线建议，照搬就是直接推线上。别照搬。

仓库没有 `.github/workflows`，**PR 上不会自动跑任何门禁**。门禁在本地：
`npm test && npm run typecheck && npm run audit`。


### 🔓 功能线可以并行（功能早就拆好了，不要再说"都挤在 App.js"）

```
src/features/journal/   手账
src/features/travel/    分账 / 行程
src/features/world/     世界打卡
src/features/wordbank/  词库 / 词场 / gloss
src/features/review/    复习    src/features/kana/  五十音
src/features/home/      首页    src/features/learn/ 学习
```

**不同 `src/features/*` 目录的任务可以同时进行，不需要开分支隔离，
也不需要拆 `App.js`（`App.js` 只是壳 + 词卡详情页，31 个顶层函数）。**

### 🔒 但这几个是全线共享的，必须串行

```
src/lib/sync.js              ← 同步链，每条线都碰
src/lib/storage.js           ← 本地存储
src/lib/supabase.js          ← 远端
src/lib/schema*.sql          ← 表结构（尤其 schema.apply-all.sql）
assets/content.fallback.json ← 内容包（见上，全局互斥）
App.js                       ← 挂载点；改动通常只有几行，按 commit 顺序串行
```

**新功能的正确形状**：写成 `src/features/<线>/` 下的新文件，
**在 `App.js` 只留几行挂载点**。这样两条功能线的唯一交点是那几行，
按 commit 顺序落地即可，不会真冲突。

### 并行前必须回答的两句

1. **这两条线碰同一个共享文件吗？** 碰了就串行。
2. **哪条需要负责人做决定？** 两条都需要的话，并行只会让他同时被两边等着 ——
   这不是加速，是把瓶颈翻倍（见 ACTIVE.md「卡在谁身上」那张表）。

## 三、并行规则

| 能并行 | 不能并行 |
|---|---|
| 不同文件的纯函数 + 测试 | 任何两个改 `assets/content.fallback.json` 的任务 |
| 各自产出 `staging/` 报告的只读分析 | 两个都写 `App.js` 的任务 |
| 文档 / 统计脚本 | 内容窗口里的任何两步 |

**subagent 可以并行分析，但写内容包必须合成一个 commit。**

## 五、报告模板（做完写哪里）

1. **`docs/handoff/ACTIVE.md`** —— 覆盖成本轮状态：当前工单是哪张、各步完成情况、还剩什么、下一步。
2. **`docs/handoff/CC-REPORT.md`** —— 追加一节，必须包含：

   ⚠️ **不要读整份 CC-REPORT 再追加。** 它只保留最近 3 轮（更早的在
   `docs/handoff/archive/CC-REPORT-archive.md`，**那份任何时候都不要整份读**，
   要哪一节就 `grep -n '^## '` 找行号再 `sed -n 'A,Bp'` 只读那一段）。
   追加时直接往文件末尾写，不需要前文。

   - 每个 commit 的实际改动范围与 hash
   - **改了内容包的，附前后 `node scripts/content-stats.mjs` 的对比**（哪些数字变了、为什么）
   - 与工单不符的事实（工单里的数字是实测的，但只测过本地 fallback；对不上以你实测为准并写清楚）
   - **你想改但忍住没改的地方**
3. **`docs/handoff/DECISIONS.md`** —— 只在产生了新的产品/事实裁决时追加，附可复算依据。

### 5-1 每个数字必须附「怎么复算」

报告里出现的**每一个数**，旁边给一条可直接粘贴运行的命令：

```
Gloss 覆盖 28,903 / 31,256（92.47%）
  复算：node scripts/gloss-coverage.mjs | grep '^gloss coverage'
```

人工判读的数（例如「38/68 误命中」）没有命令，那就写清楚：**判读对象是哪一批、
判据是什么、样本是否已贴进报告**。

**为什么**：复核方核一个数的成本，决定了它会不会被核。要粘贴就能跑，不要重写脚本。

### 5-2 报告顶部必须有「异常自查」一节

在报告正文之前，你自己先答这三个问题：

1. 这一轮哪些数字**和上一轮差了 2 倍以上**？逐条给解释。
2. 有没有哪个数**你自己也说不清是怎么来的**？直接说不清楚，不要编解释。
3. 有没有哪一类是**判据决定的、不是测出来的**？（例如某个分支永远走不到，
   某一类的定义直接决定了它的数量）

**为什么**：2026-08-25 有两次，报告里的数字与前一轮差一个数量级
（`91.2%` vs `100%`、真·缺词 `50` vs `604`），都是复核方自己抽查才发现的。
**这一节由你写，抽查就不用做。**

### 5-3 修复类工单：点名决策指标，并给它的前后值

工单会点名**哪个数是决策指标**。报告必须给出这个数的**修复前 → 修复后**。

其他数字的前后对照是加分项；**决策指标的前后对照是必需项，缺了这一轮不算完成。**

**为什么**：2026-08-25 的单字误命中修复给了覆盖率对照（93.07→92.47）和
单字占比对照（34.06→27.39），**唯独没给误命中率的修复后值** ——
而那是唯一能决定「推不推」的数。修了，但不知道修好没有。


### 5-4 工单必须在开头写死「本轮决策指标 = X」

**写工单的人负责点名决策指标，执行的人负责给出它的前后值。**
没点名，执行方不会自己找出来 —— 这一点已经证实过三次。

而且**决策指标必须是「会造成伤害」的那个数，不是合计率**：

| 反例 | 问题 |
|---|---|
| gloss：给了覆盖率 93.07→92.47、单字占比 34.06→27.39 | 两个都不是决策指标；真正的「误命中率」没测 |
| 词场：门槛设在「中文有问题合计 15%」 | 把「意思错 2.5%」和「不像人话 10%」混成一个数；前者误导用户，后者只是难看 |

**指标定错，数就白测。** 定指标时问一句：*这个数变差，用户具体受什么伤？*
答不上来的，不是决策指标。


### 5-5 省上下文：不要整份读大文件

**执行方的上下文被大文件吃掉，会导致中途压缩、丢掉工单要求。**

| 文件 | 怎么读 |
|---|---|
| `docs/handoff/ACTIVE.md`（~90 行） | **整份读，每轮必读** |
| `AGENTS.md`（~250 行） | 整份读 |
| `docs/handoff/CC-REPORT.md`（只留最近 3 轮） | 需要时读；**追加直接写末尾** |
| `docs/handoff/archive/**` | **永不整份读**；`grep -n` 定位后只读那一段 |
| `App.js`（6000+ 行） | **永不整份读**；`grep -n` 定位后读那一段 |
| `assets/content.fallback.json`（8005 条） | **永不整份读**；用 `node -e` 只取需要的字段 |
| `SOUL.md` / `RULE.md` / `CLAUDE.md` | 只在工单点名时读 |

**工单里没点名的文件不要"为了稳妥"顺手读一遍。**
需要历史结论时，优先读 `ACTIVE.md` 的摘要，而不是回溯 CC-REPORT 原文。


### 5-6 定期派一次冷启动审计（已两次证明有效）

**审计方看不到本会话的对话与报告，因此不共享它的盲点。**

到 2026-08-30 为止跑过两次，两次都抓到了常规审查漏掉的东西：

| 轮次 | 抓到什么 | 为什么常规审查漏了 |
|---|---|---|
| 词场 + gloss | **82/249 条词场在设备上显示错误中文**；我们"修好"的单字闸门第四参从未被渲染端传入，fail-open | 审计侧验了纯函数输出，没验调用方能否拿到那个参数 |
| 同步链 + 发布契约 | **4 条必修**：口袋会被云端空表清零、补传静默建匿名账号、删账号照片成孤儿、发布闸门会放行跨分支误发布 | 那三处**零测试覆盖**，而门禁全绿 |

**什么时候派：**

- 改完「测试输入」与「运行时输入」可能不一致的代码（对齐、渲染、同步）
- 动内容包 / 发布链之前
- 一段时间没审过的子系统（建议每 5–8 轮一次）

**简报怎么写（关键，写错就白派）：**

1. **不要告诉它已经发现了什么** —— 否则它只会来确认你的结论
2. **明确写"不要相信 docs/ 里的说法，自己验证"** —— 我们有 4000+ 行报告，
   冷启动 agent 最容易做的事就是复述它们
3. 要求**贴实际跑的命令和输出**，不是推测
4. 写明**"没找到问题也要说，编造问题比漏掉问题更糟"**
5. 给文件范围和"不要整份读"的约束（见 5-5）

**审计结果要自己复算再采信** —— 两次我都逐条复算过，数字都对，但这是必须做的一步。

## 六、交报告之前必须做的两件事

**跑这两条，把原始输出贴进报告。不是复述，是贴。**

```bash
git status --short          # 该提交的都提交了吗
npm run audit               # 验收标准满足了吗
```

**为什么是这两条**：2026-08 有三次报告与实际脱节，全都能被它们当场抓住 ——

| 报告说 | 实际 | 哪条能抓 |
|---|---|---|
| 「拼句专项测试 5/5」 | 那 5 条 `npm test` 跑不到，是手动单跑的 | `npm test` 的总数对不上 |
| Harness v1「已完成」 | 三个文件全在工作区，一个都没提交 | `git status` |
| 「23 个既有 FAIL」 | 工单验收标准写的是「FAIL 0」 | `npm run audit` |

**没提交 ≠ 完成。写在磁盘上不等于进了仓库。**

**验收标准不满足就不叫完成** —— 如果你认为标准本身有问题，
在报告里说明并**停下来问**，不要把不合格重新描述成现状。

## 七、诚实要求

- **跑不到的测试不算通过。** 手动单独跑的要写明「手动单独跑」,并说清为什么它不在 `npm test` 里。
- **一个永远红的检查等于没有检查。** 发现既有 FAIL,先判断是真问题还是误报,不要当背景噪音接受下来。
- 「已完成」和「待项目所有者执行」要分清（尤其 SQL 迁移、远端发布）。
- 不要用「已验证」形容只是「跑通了」的东西。
- LLM 产出只能是 candidate，**不能直接进 `publication`**。两个模型一致不是两个来源。
